# 01 — What is wrong, and why

Every finding has an ID, the evidence (measured on 2026-10-21 unless stated), the root cause, the impact and the task that fixes it.
Evidence screenshots are in [`evidence/`](evidence/). Measurement details and sources are in [`09`](09-research-and-measurements.md).

Severity: **S1** = breaks the core promise or loses data / safety; **S2** = a person notices and is hurt by it; **S3** = polish.

## B. Speed: playing what you don't own, and importing

| ID | Finding | Evidence | Root cause | Task |
|----|---------|----------|-----------|------|
| **B1** S1 | **38 s from tap to sound** for a song not on the server (search → tap). | App: 38.3 s ("Maria También"). Server log: 33–35 s in "searching", then extraction, then a growing file is streamed. | See B2 and B3. | P1-01 … P1-05 |
| **B2** S1 | **The search step wastes 30+ seconds.** For one song the server starts up to **8 separate yt-dlp programs**: a plain YouTube search (`ytsearch8`, measured 3.6–9.4 s), a YouTube Music search page, then **up to 5 full extractions of watch pages** (`yt-dlp -j`, 3.8–4.5 s each, ~1 MB of HTML each) only to read each candidate's title and length, then one more extraction to download. | `server/encore-fetch/encore_fetch/resolve.py` (`YtDlpResolver.resolve`, `music_candidates`); timings in `09` §2 | Using a downloader as a search engine. YouTube Music's own search API returns title, artists, album, duration and video id in one ~1 s JSON call (`ytmusicapi`). | P1-01 |
| **B3** S1 | **Every call starts a new yt-dlp process.** 0.6 s of start-up each, no warm player-JS cache, the JavaScript challenge solved again every time. | `run_command()` = `subprocess.run` per call; `yt-dlp --version` 0.60 s, `import yt_dlp` 0.61 s | Stdlib-only design choice | P1-01 |
| **B4** S1 | **The server's internet download was capped at 3 Mbit/s** by the owner's homelab dashboard (CAKE shaper on the Proxmox host). Every song you don't own had to come down through that cap before you could hear it. Nobody had found the cap: docs blamed "the line" or "YouTube throttling". | 8 MB at the cap: **70 s**; cap off: **5 s**. A 7.6 MB song: **71 s** vs **5.5 s**. The owner then raised it (now 15 Mbit/s). | Not a code bug; a hidden environment constraint that measurements never isolated | Owner's choice (done); design rule in `04` §6: never assume one particular line |
| **B5** S1 | **Imports download every song's audio before they are "done"**: 200 songs → "about 2.3 hours left". | `evidence/a11-*`; the import page itself says "about 12 seconds a song" | Import = copy audio. Spotify's import is a copy of a *list*. | P2-04, P2-05 |
| **B6** S2 | **Imported YouTube Music songs are searched for again, one by one**, although the playlist already gives each song's exact video id. | Log: "Nelly - Dilemma searching +0.0s … +7.2s … downloading +14.7s"; "Eminem - Without Me searching +35.2s" | The import queue feeds titles into the generic "play by name" path | P2-04 |
| **B7** S2 | **Docs reported speeds that were never true for a person** ("9–13 s", "line-limited ~450 KB/s", "tap → sound 3.6 s" which only holds when the page was open for 10+ s first). | `old-app/docs/19` §5a, §8 | Measured the best case; never the person's case (search, then tap at once) | `07` §3 (what a measurement must say) |
| **B8** S2 | **Spotify links give at most 100 songs**, and Spotify's developer API now needs the app owner to pay for Premium (February 2026), so the "Spotify developer app" route planned in ADR-101 is dead. | Embed page measured: 100/100/69 songs in 2.2–3.5 s; Spotify Feb 2026 changes (`09` §4) | External change | P2-06 |

## C. Architecture

| ID | Finding | Evidence | Root cause | Task |
|----|---------|----------|-----------|------|
| **C1** S1 | **Seven separately built server programs** (fetch, people, admin, quality, recs: Python; hub: Dart; plus the reference kit) **and up to five third-party ones** (Lidarr, slskd, Soularr, Firefox, Tailscale) for what is a home music server. Each has its own port (4533, 8701, 8703, 8704, 8705, 8800), its own copy of the music-server client (`navidrome.py` ×4, `textnorm.py` ×2) and its own way of checking logins. | `server/` tree; `compose.yaml` (573 lines, 8 profiles) | One service per feature, added session by session | P3-01 |
| **C2** S2 | **The app must find each service in two different ways**: by port at home, by path (`/fetch`, `/people`…) through the public address. A "one answer" endpoint and a `ServiceFinder` exist only to paper over this. | `old-app/docs/53` §0, `instant_controller.dart` (`fetchServiceCandidates`) | No single front door | P3-01 (one origin) |
| **C3** S1 | **A song's identity is the music server's file id.** A song without a file cannot be in a playlist or liked, so the code grew a special "instant playlist" page (ADR-102), "pending likes" (ADR-093), and an "upgrade map" that the phone must apply before drawing likes because swapping a file changes its id (ADR-107, measured in `old-app/docs/46` S1). Each patch is a new way to lose a like or a playlist entry. | ADR-093, 102, 107; `old-app/docs/53` §4 calls the applier "the dangerous one" | Treating Navidrome as the source of truth for things Navidrome cannot represent | P2-01, P2-02 (Encore owns the person's library; files are attached to songs) |
| **C4** S2 | **One library folder per person.** A song two friends play is downloaded and stored twice; rules for folder names (`PEOPLE`, `PERSON_FOLDERS`), read-only mounts and a provisioner exist only for this. | `compose.yaml` `encore-fetch` env; `encore_user.py` | Privacy was solved with folders instead of with the library model | P2-02, owner decision D-2 |
| **C5** S1 | **The admin service holds Docker's socket** (as powerful as root on the host) so it can start a Firefox container in which an owner signs into Google, and restart containers. | `compose.yaml` `encore-admin` volumes | Building the "Google sign-in" feature (C6) | P3-04 (remove) |
| **C6** S1 | **The server asks people to sign a Google account into it** to raise YouTube's allowance. yt-dlp's own docs warn that accounts used this way get banned; for most people their Google account is their Gmail, photos and Android phone. | `old-app/docs/50`; `server/encore-admin/encore_admin/signin.py` | Trying to beat YouTube's per-address allowance on the server | P3-04; design `04` §5 (no bulk, no accounts) |
| **C7** S2 | **Images are built on the user's machine** (`build:` in compose), ~5 GB of images with every profile, no published image, no update command. | `docker images` on the dev VM: fetch 1.0 GB, soularr 1.6 GB, firefox 1.2 GB ×2 | Developed on the owner's machines only | P3-02 |
| **C8** S2 | **The Jam wraps every play.** `playbackFacadeProvider` is always a `JamPlaybackFacade`, so a niche feature sits on the critical path of every tap. | `lib/features/providers.dart` | Field-test request "the Jam is the normal player" implemented by wrapping, not by a session layer | P4-02 (Jam rebuilt as a layer on the live channel) |
| **C9** S2 | **Logins travel as Subsonic tokens in URLs to every service**; the app keeps the password to make them. | `encore-fetch` README "Authentication"; every service validates by calling Navidrome | Reusing Subsonic's 2005-era scheme for new services | P3-03 (one gateway, device tokens) |
| **C10** S2 | **The "quality tier" depends on Lidarr's metadata server**, which had a long outage in 2025 with one person holding the keys; Soulseek hit rate unknown, legal exposure high. | `09` §6; `old-app/docs/46` "real network: zero peers answered" | Built before the core worked | P4-04 (quality tier rebuilt on song refs, switched on by the Host) |
| **C11** S2 | **No server-side playback state.** Pausing at 2:31 and continuing at 2:31 on another device, and "only one device plays at a time" (owner requirements, 2026-10-21), are impossible: Navidrome's saved queue holds only library songs and does nothing about two devices playing. | Owner's message 2026-10-21; no such module exists | Not a requirement before today | P2-08, P2-09 |
