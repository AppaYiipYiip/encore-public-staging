# 31 — Connecting to a server: the network, the address, who answers, signed in or not

> **In short.** The state tables of connecting: is there a network, which address is the server's, is it really my server (a key it proves), am I signed in. Every row (`CN-n`) says what the person sees, whether it is Built, Designed or Open, and which test pins it. A change to one of these states changes its row in the same pull request.

The state tables for everything between "the phone starts" and "the phone may ask its server for music". Written 2026-10-23 from the code (files named in the
**Where** column) and from the decisions in `11` ADR-R40 (the key as identity, the server's own addresses). Joining a server and the account's life are in `32`;
playing and what happens when the connection breaks while playing are in `33`.

**How to read the tables.** Every row has an ID (`CN-n`), what causes it, what the person sees, a **Status** and a **Test**.
**Built** = the code does it and I read the code. **Designed** = decided in the plan, not in the code. **Open** = nobody has decided; collected at the end.
A **Test** of "none" is a debt, not a decision. A change that touches one of these states updates its row in the same pull request (`30` §0).

## 1. Three questions, asked in this order

A phone with a saved server asks, at every start and after every network change: **(1)** is there a network at all? **(2)** which address is my server
at, and is it really my server? **(3)** am I signed in there? Each has its own states below. The screen shows the **first** answer that is "no": a person
with no network is never told "sign in again".

### 2a. The one state of "can I reach my server" (P1-17, AUDIT B-17)

Three raw facts, ONE derived state; every reader (the strip, the grey rows and the words under them, the player, the settings pages, the outbox) reads the state or one raw fact it is made of, and nothing else exists. The state is `serverReachabilityProvider` (`app/connection.dart`), computed by `reachabilityOf` (`domain/server_reachability.dart`, pure Dart).

**Raw facts** (never read a presentation): the link (`networkKindProvider`: none, wifi, mobile); Android's own "internet found" (`networkValidationProvider`, a point-in-time read, asked by the state at the moment it decides and never through a screen); what the last look at the addresses found (`EndpointResolver.finding`: `unknown`, `answering`, `silent`, `anotherServer`; `anotherServerAtProvider` gives the host for the words).

| State | Made of | What the readers do | Test |
|-------|---------|---------------------|------|
| `unknown` | a network and the server not looked at yet (the first second of the app, a change of network) | nothing is greyed, nothing is said, a song may be tried | `server_reachability_test.dart`, `connection_test.dart` |
| `ok` | a network and the server answers (Android's answer is not asked: a home Wi-Fi with no line out is fine) | everything plays | same |
| `noNetwork` | no network at all | **at once** for the rows and the player (P1-09); the strip says it after 4 s (a blink of the radio is not news); "You're offline." | `connection_test.dart`, `can_reach_server_test.dart` |
| `noInternet` | a network, a silent server, and Android found no internet (4G with no data, a sign-in page) | after the 4 s blink filter: rows grey, "Not downloaded. Connect to play it.", "You're offline." | same |
| `serverAway` | a network, a silent server, internet found (or Android cannot say) | after the 4 s blink filter: "Not downloaded. Can't reach your server.", "Can't reach your server." | same |
| `wrongServer` | an address answered with the key of another server (CN-11) | after the 4 s blink filter: the strip names the address; the rows say "your server" | same |

**One blink filter, in the state:** entering `noInternet`, `serverAway` or `wrongServer` waits 4 s; `noNetwork` is at once; leaving any of them, and changing from one to another, is at once. **The strip is a presenter:** it says an outage once, for 5 s or until the cross, and not again until everything has worked for 10 s. **A fresh look is newer than the state:** the player asks the server once before it refuses a song (`PB-F7`; `recheckServer`: no network is answered at once without a look, no server is `unknown`) and believes that answer for the tap that asked; the look also feeds the state. **The player has ONE read and ONE recheck** (`PlaybackEngine(reachability:, recheck:)`) and one listener (the state leaving "away" starts a song that waited); its own retry timers (`PB-F7`: after 1, 1, 2, then every 3 s) only DRIVE looks, they define no notion. **The Jam is not part of it** (the strip no longer says "Reconnecting to the Jam"; the Jam screen shows its own). **The music server is not part of it:** whether Navidrome answers shows only as the failure of a browse call, and the sync reports it apart (`SyncStats.browseFailure`, AUDIT B-77). The test that fails when two readers disagree is `can_reach_server_test.dart` ("every reader says the same thing in every state").

### 2b. Which KIND of server (P1-17, AUDIT B-17, B-78)

The second question every screen asks, answered once: `serverKindProvider` (`app/server_kind.dart`), read by the words and offers that depend on it (Home's empty state, the catalogue pages, Settings > Your server, the import page, the request portal) and by a tap on a catalogue song (`tap_play.dart`).

| Kind | What it means | What the readers do | Test |
|------|---------------|---------------------|------|
| `detecting` | the session is still being built, failed to build, or is a plain session whose server has not yet answered DEFINITELY | a tap on a catalogue song WAITS for the answer (D-24, at most 12 s); nothing that is for one kind only is offered (the request portal is not) | `server_kind_test.dart`, `session_detect_test.dart` |
| `plain` | no server, or the phone KNOWS this is not an Encore server: the server answered "not found" or a web page of its own to `GET /info` (B-78: a 503, a 429, a refused login or no answer is NOT such an answer) | the old way; the request portal is offered where there is no instant-play service | same, `request_portal_offered_test.dart` |
| `encore` | the phone has been moved onto an Encore server | songs are references the server plays itself; playing does not save | same |

`instantAvailableProvider` is NOT a kind: it is the "Play songs your server does not have" switch plus a service found, a capability that stays. `requestPortalOfferedProvider` is a rule over the two (`plain` and no instant-play service) and goes with the portal (P2-07). The session's mode is PRIVATE (P1-17 slice 5, decided by the lead): `ServerSession.encoreApi` is the Encore server's API when this phone is on an Encore server and `null` otherwise, and it is the one fact `serverKindProvider` is made of; code that talks to the Encore server (keep, news, people, imports, release save, the player's address builder and look-ahead, the instant-play backend) asks the session for `encoreApi` and gets one exactly when the kind is `encore` (`server_kind_test.dart`, `session_encore_test.dart`); everything that only words itself or offers something by kind reads `serverKindProvider`. Readers of the raw link that only ask "is there a network at all" (the Library's offline opening, the cover and lyrics prefetch, the downloads' "waiting for a connection") read `networkKindProvider`: that IS the raw fact the state's `noNetwork` is made of, so they cannot disagree with it. The line under a download says "waiting for a connection" for `noNetwork` AND `noInternet` and "waiting for your server" only with internet found (`phoneWaitProvider`).

**Rule that follows from S2 (Built, P2-19 slice A):** a login, a token, a signed address or a query credential is sent **only** to a candidate in `verified` (or `legacy`, which gets the credentials it always had but no probe with them). Every request, stream and cover is built from one address, `endpoints.currentUrl`; with verification on it is only ever an address that proved itself, and otherwise `unverified.invalid`, a name that can never be reached (`EndpointResolver.requireVerified`, `unverifiedUrl`). The first race has to finish before the first request leaves the phone (a round trip: measured in the slice A pull request), a race that finds nothing takes the last good address back, and a **change of network** (`networkKindProvider`) invalidates it at once and runs the race again. Tests: `endpoint_resolver_test.dart` (the gate), `session_verification_test.dart` (nothing but the question reaches an impostor).
