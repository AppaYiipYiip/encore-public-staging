# 18 — Data model and the migration from today's installs

Why: P2 changes where a person's library lives (`04` §3). Without a written schema and a migration path, an agent would either break
the owner's existing data or keep the old model alongside the new one forever.

Migrations: numbered SQL files run at start-up inside a transaction, with a backup copy of the database taken first
(`/data/backups/encore-<version>-<time>.db`); a failed migration restores it and the server refuses to start with a plain message.

**After the migrations, FIRST at every start (`keyrepair.repair`, P2-25 slices 2 and 3, audit B-37).** The stored `song_ref.norm_key` is how a song described again finds its ref, and it is a function of the text fold. **The plan (a read) runs at EVERY start** (THE PLAN ALONE, which is the cost of every start: 0.07 s on the 3,394 refs of the copy of VM 108's database; 3.4 s on 200,000 synthetic refs with nothing stale, 3.6 s for the plan of the first start, which judges every ref; measured on the code of `66735f1`, Python 3.12); something is written, and a copy taken, only when it finds something. **The first start after the fold changed** (`setting.textnorm_revision` lower than `textnorm.TEXTNORM_REVISION`; a database that never had the setting was made by the old ASCII fold: revision 0) rewrites every key from the ref's own artist and title and judges every ref the old fold damaged; the revision is written last. **Every later start** rewrites only a key that is NOT what the fold makes now (the keys an older image wrote after a rollback, the rollback hole; a bump of the fold nobody wrote down) and judges damage only for those refs, so the worklist the rehome empties stays empty and a picture the cover finder found later is never voided again. A database of a NEWER revision is left alone (never rewritten down). One transaction, after a copy of the database (`/data/backups/encore-before-key-rewrite-<time>.db`, the path logged). **The invariant: the repair never writes without a copy it can be undone from, as far as a check at start-up can tell** (the tombstone keys it sets to NULL and the pictures it voids come back from nothing else), and it holds in two layers, neither of which depends on the ORDER of the copies, because that order cannot be trusted: a copy's name is the LOCAL time of the clock that made it, a clock goes back (the end of daylight saving time repeats an hour, a time sync steps it, somebody sets it), and a file's modification time comes from the same clock. (The first version ordered the copies by their names; a reviewer reproduced it: with three copies named in the future the copy just taken was the OLDEST of four, the prune removed it, and the repair went on with a path that did not exist and logged it as kept.) **Layer 1, by construction:** the prune is told which copies must stay (`Database.prune_backups(..., protect=...)` is required: the copy just taken and the one the last COMMITTED repair used) and never takes them as candidates; the copy an attempt takes is recorded by name (`setting.textnorm_backup_pending`) in its own committed write, right after it is taken, because the rewrite may roll back, and the next start reuses exactly that copy (not repeated: a repair that fails for good takes one copy, not one per start), and only while it is still there and looks like a SQLite database (a file that merely sorts newest is not an earlier attempt's copy); the repair that commits records the copy it used (`setting.textnorm_backup_used`) and clears the pending record in the same transaction, so a copy a committed repair used is spent and a later repair after a rollback is never blocked by an old copy; at most 3 copies of this label are kept (a rollback loop cannot fill the disk; the copies of a migration and of the merge are never touched). **Layer 2, at the point of writing:** the first thing inside the write transaction, before any write, the repair checks that its copy EXISTS, is NOT EMPTY and STARTS WITH THE SQLITE HEADER (the first 16 bytes, `SQLite format 3` and a zero byte: `keyrepair._is_a_copy` reads them and nothing else); if not it writes nothing (no key, no worklist row, no revision), logs ONE error line and the server goes on (the next start takes a new copy). **That is all it checks: it is NOT an integrity check of the copy's contents.** Nothing opens the copy, runs `PRAGMA integrity_check` or restores it, so a copy cut short (a full disk, a kill in the middle of the copy) that still begins with the header passes; what stands behind the header is how the copy is made (`Database.backup` is `VACUUM INTO`: a whole new database file or an error, taken under a read lock) and Layer 1's rule about which copy is relied on. Nobody may read "can be undone from" as "restore-tested". **The cost:** with the clock gone back the order of the names can be wrong, and then a spare copy goes before another (an older spare is kept instead of a newer one), never the copy the repair relies on; a reused copy can be older than the start that used it (a repair that fails for a week is backed by the copy of its first attempt). A rewrite NEVER merges refs. A ref is *damaged* when its own text lost a letter or a digit in the old fold OR when its STORED key has an empty artist or title segment (`slipknot||sic`: all ASCII, one key for every song of the band that has a bracket in its name); a damaged ref that holds a library file goes on the worklist `ref_recheck`; tombstone keys with an empty segment become NULL; the Deezer picture of a damaged ref the catalogue never identified is voided (the finder asks again). It is idempotent, rolls back whole, logs counts and ids only (one ERROR line per start when it fails) and never stops the server. **An invariant the plan depends on:** a ref's stored key is always `norm_key(first artist, title)` of the text the ref has now (the only write of a key is the INSERT of `refs.resolve`, and nothing rewrites a title or the artists of a ref; `tests/test_keyrepair.py` makes eleven kinds of song with the real code and checks that a start writes nothing for them). **A later item that rewrites a ref's artist or title (N-26 slice 5, N-28) must rewrite the key in the SAME transaction**, or the next start takes the ref for one an older image made: it rekeys it, takes a copy and, for a text in another alphabet, lists it on the worklist and voids its catalogue picture. **The Unicode pin, below, is why the server does not start on the wrong Python.** A later change of the fold is the same mechanism with a higher constant; THE WHOLE REPAIR, once (the plan twice, the copy of the database and the writes: NOT a per-start cost) took 0.28 s on the copy of a real database (3,394 refs) and 8.3 s on a synthetic 200,000-ref database (51,702 keys rewritten); the 3.4 s of the plan is what every later start of such a server pays.

**Hourly, in the library link: the rehome (`rehome.py`, P2-25 slice 4, audit B-37; built, not walked, not deployed).** The scan keeps a file on the ref that holds it, whatever its tags say, so the files the old fold glued onto the wrong song (one ref holding five files of five songs) would stay there for ever; the rekey above only lists those refs. While `ref_recheck` is not empty, `scanner.link_library` judges every LIBRARY file of a worklist ref (not the keeper's: source `youtube` or `quality`) by the tags of the song it reads, **against ONE state** (the second review round of PR #118, 22 Nov 2026): each page only NOTES the tags of the worklist's files, and nothing is decided or written until the music server's whole listing has been read, linked (the scan's own transactions) and pruned; then every file is judged oldest first, the moves are applied 100 at a time in write transactions (each move judged again inside its transaction), and the verdicts a move can change are judged again, round by round, until a round moves nothing (the last file of a liked song once a file has arrived, a nameless file once a song a move made carries its id, and a kept or moved file whose tags name a song a move made, by its id or by its name (a live name outranks a tombstone), which now fits as well as another; typically two rounds, at most one more per file that moved; `MAX_ROUNDS` is the second layer). The first build decided page by page and its decisions read state that the same pass changes, which the adversarial tester proved on random worlds with three permanent defects: the last-file guard counted a row the prune removes later in the same pass (a liked song kept its like and lost its only listed file; 28 of 1,500 worlds), a move FILLED the length or an id of the song it moved a file onto so that a sibling file no longer fitted it at the next pass (a hold only the rehome's own write made), and a file that arrived on a liked song freed that song's other wrong file only at the NEXT pass (a second pass that wrote again and took another copy; 22 of 500 worlds). **The costs, stated:** a pass that stops early (the music server stops answering, the process dies) decides and writes nothing, so a library whose listing never completes is never rehomed (the worklist was already emptied only by a complete pass); and the pass keeps the tags of the worklist's files in memory until the listing is complete (about 330 bytes a file: 67 MB more than the 130 MB the worklist's rows already take, 197 MB in all, at 200,000 worklist files, measured; a real worklist is the damaged refs only, thousands); **every round that makes a song judges the kept and the moved files again** with `refs.candidates` (`_files_naming`): at 200,000 worklist files and one move the attacker measured 20 s of a 43 s verdict phase (a whole pass 69 s on a machine with 40 percent other load), and a pass with no move does not pay it. **A file is re-pointed only when nothing says it may be where it is: a wrong move is worse than none** (the rule of the review round of 20 Nov 2026, the same as the N-34 ruling). It STAYS, and its ref STAYS on the worklist with ONE log line (ids only) saying why, when (1) its ref is one of the refs its tags name first (`refs.matches`: the first tier of evidence of `refs.candidates`, which is also what `refs.find` takes its answer from: ids first, then artist + title + a length within 3 s, then the tombstones; two refs of one song are both answers, so a duplicate keeps its file and `refmerge` folds the pair), (2) its ref is ANY plausible answer of `refs.candidates`, not only the first tier (a ref that merely has the same name next to the ref an ISRC names: the review's case, a like on R and a duplicate X holding the ISRC, which used to re-point the file R to X and strand R's like for good because the two share no file; a ref that absorbed a duplicate under the tags' name), or its own artist and title are the tags' whatever its length says (`refs.names_ref`: a ref whose length was filled in later is exactly the ref a file must not be moved from on that ground; the cost is that a longer cut of one song on one ref cannot be told apart and stays too), or (3) it is the LAST file of a song a person owns (`ref_janitor.owned_by_people`: the janitor's own `POINTERS` without the files, so a new table of somebody's things is owned with no other change; **"another file" is a file this pass leaves alive**, `link_listing.Listing.alive`: the music server lists its id, or the row was attached after the pass began, or it has no music server id, which is the very test `scanner._prune` removes rows by, so a row the prune removes in the same pass is no file the song keeps; asked inside the write transaction, so the second of two moves stays, and again in the next round when a file has arrived on the song): a like, an entry or a play would stay on a song with no file. Otherwise the `song_file` row is RE-POINTED to the ref the tags name, or to a new one (`refs.resolve_keeping_identity`: a song a move MAKES is described in full by its own file, as a fresh scan would; **a song that exists keeps its length and its ids**, which are what the next file is judged by, while an album, a year or a track number still fills a gap), with its id, `added_at`, `meta` and `source` kept (a delete and a re-attach would open a window of `file: null` on the feed in which a phone drops a download); a target that already holds the same file keeps its row and the wrong holder's is dropped; one preferred file per ref is restored on both, and at the end of the pass the old song prefers a file JUDGED KEPT (or a keeper's), never the newest one that stayed only because nobody could judge it (read from `ref_recheck.moved`, which is committed with each move, so a pass that failed after a move is put right by the next complete one; `ensure_one_preferred`'s rule, which `refmerge` also uses, is unchanged); `file_log` and the holders' change feed are touched for both refs. **The placeholder artist** (`[Unknown Artist]`) is judged by ids only, and a file with no usable tags is not judged: both stay, **and their ref stays on the worklist** (nobody could check its files, so the pairs held for it stay held). A file the music server LISTS with no usable tags is not "gone" (the prune removes the rows of files the listing lacks, no longer of listed ones, whoever holds them), so this holds through the real hourly pass and not only when the pass is driven by hand (`tests/test_rehome.py`, through `link_library` with the prune on). **The cost, stated:** on a Host with such a file, or a doubtful one (above), the ref stays on the worklist and every pair held for it stays held; what lets each ref go depends on why it is held: a file with no usable tags, or the placeholder artist with no id, until the Host tags the file or removes it; a song that fits its tags as well as another (R has no ISRC, X holds the one the tags carry), until the file is removed or the ISRC is taken out of its tags (tagging cannot help: the tags are already right, and R and X share no file, so `refmerge` never folds them, so on that Host the ref can stay for good); the same name with another length, until the song's stored length is corrected or the file is removed; the last file of a song a person owns, until the song gains another file (the next pass then moves the wrong one) or nobody owns it any more. The visible reminder is the `rekey_audit` FAIL, which names the files. On a Host where a ref is held for good, N-36's trigger (the worklist empty on every install) never fires: what N-36 does with a ref held by design is the lead's decision (asked in PR #118). **It changes `song_file` rows and nothing else:** no file of the Host's music is renamed, moved, retagged, written or deleted, and a like, a playlist entry, a play, a saved release and the saved queue stay on the ref that holds them (the old ref keeps its id and the first title the person saw; no `ref_merge` row, no `ref_gone` row, no new feed: the phone reads the CURRENT state of both refs from the files feed it already reads; `tests/test_rehome.py` and `app/test/data/encore/encore_split_test.dart`). **The worklist is emptied only by a COMPLETE pass**: a ref leaves it when every library file it holds was decided (kept, or re-pointed elsewhere) or is gone (a pass that only adds cannot say a file is gone, so a ref with a file it could not see stays, with a line that says so; the hourly pass that prunes finishes it); the rows leave it 500 at a time, one write transaction each (`RELEASE_CHUNK`, pinned at 500 by `tests/test_rehome.py`: 1,001 refs are released in 500, 500 and 1; measured on 200,000 synthetic refs, Python 3.12.13, 22 Nov 2026, **three runs on a machine that was NOT quiet** (a browser, Discord and Phone Link open; CPU load 2 to 52 percent when sampled): 400 write transactions release rows (401 with the one that spends the copy), each held the lock for a median of 10 to 12 ms in the transaction (the worst 64 ms) plus a median of 9 to 10 ms to commit (the worst 121, 269 and 271 ms, a commit that checkpoints the WAL), so the lock was held at most 0.14, 0.28 and 0.28 s; ONE transaction for the whole worklist held it for 4.7 s on the same machine; the price of the chunks is that the whole release takes 17.0, 19.3 and 18.0 s instead of 5 s (the first round's code, measured back to back in the same state, took 14.8 and 15.7 s; on a quiet machine the lead measured 3.9 s, and 1.2 s for one transaction; the independent attacker of 23 Nov measured, on a quiet machine, a median of 19.9 ms, at most 84 ms and 8.1 s in all for the 401 transactions, and on a loaded one a median of 49.5 ms, at most 549 ms and 24 s); **Hourly, in the library link, BEFORE the cover finder: the album pass (`album_pass.py`, N-34 slice 2; built, not walked, not deployed).** It asks the catalogue which album the songs that have none are on (the search of the song, then the album answers of the same-recording hits, serially, as background turns at the gate), through the matcher of slice 1 (`album_finder.decide`, the one function the dry run `python -m encore_server.album_dryrun` asks with too) and writes what it answered. **Who is asked (`album_pass.wanting`, the ONE selection the pass and the dry run both call: a review fix of PR 125, so that reading the report predicts what the pass stamps; `tests/test_album_selection.py` runs both over one database):** a ref whose album is NULL, blank or the placeholder `[Unknown Album]`, with no `deezer_id`, whose `artist_basis` is a performer or NULL (never `channel` or `unknown`, N-26), that somebody has (a like, a playlist entry) or the server keeps a file of (a kept file first), that is NOT on the P2-25 worklist (`ref_recheck`: its file, and so its length and name, may belong to another song until the rehome has judged it; skipped, nothing stored), and that was never asked or whose `none` or `held` is older than 7 days or than `IDENTITY_REVISION`. One song whose matching RAISES something unexpected is logged by its ref id (no title) and skipped for this pass, nothing remembered, and the pass goes on (a catalogue id of 5,000 digits once aborted it at that song every pass: an id is 1 to 20 ASCII digits or it sorts after every real one). At most 200 songs and 300 seconds per pass; a catalogue that is resting, off or cannot be asked stops the pass and stores NOTHING (audit B-124: not even the placeholder). A song's length is the kept file's own when the music folder is known (`album_pass.length_of`, shared with the cover finder: the import's listing is 1 to 12 s off, N-11), else the ref's `duration_ms`; no length, or a name with nothing to compare, is never asked and never remembered. **What is written, in ONE transaction per song that re-reads the row first** (a ref that gained an album or a `deezer_id`, or reached the worklist, while the catalogue was asked is left alone): for `matched` `refs.release_facts_to_fill` (fill only, never rewrite: the album when it is empty or the placeholder, the track, the disc, the year, the picture of the catalogue's host, and `isrc` and `deezer_id` only when no other song holds them; nothing at all when the song already has a real album of another release; never the title, the artists, `norm_key` or `album_artist`), `touch_ref_holders` and `touch_file` (the phones learn it from the feeds they already read); for `none` and `held` only the reason and the placeholder forgotten. **The placeholder literal becomes NULL for every song the pass examines** (matched, none, held and the songs it cannot ask about, which cost no request), with the phones told when it changed; the songs it does not examine keep it (a channel's or nobody's name, a song that has an id already, a song nobody has or keeps, a song on the worklist: NOT done, and it is harmless to the display, `album_names.dart`). **A release whose title carries a version mark the song's title does not is not the song's release** (the live dry run of 24 Nov 2026 stamped a studio song with a LIVE album, the earliest of its two releases; the marks of a hit's title were never applied to the release's): `album_finder.release_markers` (the server's `VERSION_WORDS` and their plural or past forms: live, remix, acoustic, demo, instrumental, karaoke ..., plus Unplugged, Re-recorded and a possessive Version such as Taylor's Version; Remastered, Deluxe, Explicit, Clean and Radio Edit are not marks, and `Sessions` and `Tribute` are left out on purpose: too common in real album names, the cost of a miss is a re-askable `none`, the artist's discography is the remedy) refuses the release (`release_version`), the other release is chosen or the song is a re-askable `none`/`release_version_mismatch`; **a release the catalogue calls `Unknown Album` is refused too** (`release_placeholder`: matched, it would set the id and write the placeholder, a permanent match with no album), at the matcher and again in the write transaction; a song whose OWN title carries the mark may take it (the control: a remix on a remix release). **A single is never stamped** (the advisor's ruling after the live dry run of 24 Nov 2026): a song whose only same-recording release is a SINGLE is `none`/`single_only`, in the matcher and again in the write transaction, because a stamp is permanent (the later rounds, the artist's discography and a better rule, only ask `none` and `held` again, so a stamped single could never be corrected), and the eight hits of a search cannot prove that no album carries the recording; the live dry run of 24 Nov 2026 stamped singles for songs that are album tracks (`What's Luv?`, `Buy U A Drank`). **The cost is a delay**: the song stays in "Songs without an album" until the discography round, whose first measured target these songs are. EPs stay accepted. **An ISRC the song already holds is counter-evidence** (a review fix of PR 125): a recording has one ISRC, so a same-name, same-length catalogue entry that carries another one is not this recording and a permanent stamp would be a wrong one: `none`/`isrc_differs` (re-askable), checked at the search row, at the chosen release's song list and AGAIN in the write transaction (the row may have gained an ISRC since it was read); an equal ISRC, or none on either side, changes nothing. **What is withheld, never matched** (the advisor's ruling of 17 Nov 2026: a stamped album is effectively permanent because the repair of slice 5 files the song by it, so what the matcher cannot justify on evidence is a re-askable `none` with a reason, and `Verdict.withheld` keeps what the old rule would have written for the report): `single_before_album` (an album or EP carries the recording and an EARLIER single too: the album wins only inside `SINGLE_BEFORE_ALBUM_WINDOW_DAYS`, which is NOT FROZEN, so for now every such song waits), `compilation_title` (the chosen release's title carries Greatest Hits, Best Of, Collection and the other whole words of `COMPILATION_MARKERS`; a best-of called Gold or Legend that is the only candidate is accepted), `latin_spelling_only` (a non-Latin song whose only catalogue hits are spelled in Latin letters: nothing is transliterated, so it is a remembered `none` counted apart in the report). A pair is `held` (a taken `deezer_id` or `isrc`, or another song that is this one on this release, or an id another song took, or a twin made, after the matcher looked: all three kinds are asked AGAIN inside the write transaction, so every hold has a second layer): nothing is filled and ONE INFO line names the two refs and the catalogue's id, never a title. **The pass writes no file** and moves none (the album folder, the tags and the folder picture are slices 3 and 5); the artist page keeps the music server's own albums until then. **A stamp reaches the Host's disk LATER, through the keeper:** the keeper reads `ref.get("album")` at three places (`keeper.py`: the folder and file name in `_placement`, the tags in `_finish`, the search of the music server in `find_song`), unchanged by slice 2, so the album this pass writes onto a song is also what the next keep of that song (a later download, a re-keep) writes into its TAGS and its FOLDER. A wrong stamp therefore reaches the music folder through a later download, which is why no image carrying slice 2 may run on a real server before a dry run over a copy of THAT server's database has been read. **Cost, said plainly:** about one search and one to three album requests per song, spread over hourly passes; a song that stays a `none` is asked again every 7 days. **Stop-gaps (the markers `STOP-GAP(N-34 ...)` in `album_finder.py`):** the single window (unset: every lead single waits for a dry run over a library that holds enough single/album pairs to show a window; the recordings in the project hold one proven pair and three by title, all of one band, and the live run of 24 Nov 2026 found one pair in 672 songs), the compilation markers (English words; the artist's discography would replace them, a later `identity_rev` round if the dry run shows a large remainder) (the 3-second tolerance is no stop-gap any more: it was MEASURED on 24 Nov 2026 over 672 songs and their kept files, 161 of 404 name-matched songs within 3 s and a smooth tail with no cliff, and kept as the conservative edge; price: misses only). The window's removal trigger is a dry run over a library that holds enough single/album pairs to show one (about 30, the lead decides; the live run found 1 in 672 songs). `refs.recheck_pending` is called twice here: N-36 removes both calls (`STOP-GAP(P2-25 one-shot-repair; remove after 0.1.0)`, in the inventory of `tests/test_stopgap_expiry.py`). Tests: `test_album_pass.py`, `test_album_identity.py` (the migration and the facts), `test_album_withheld.py` (the ruling, the step-0 measurement, the pin of the tolerance, the window, the markers, the winning types and the fold's revision with `IDENTITY_REVISION`, which is raised by hand when the rule's code changes), `test_album_dryrun_slice2.py`.

**New keeps: the keeper asks the same question (`Keeper._identified`, `album_pass.KeepAsker`; N-34 slice 3; built, not walked, not deployed).** When the keeper has downloaded a song and BEFORE it makes the tags and the place (`Keeper._finish`), it asks which album the song is on: ONE question per new keep, and it is the pass's own question: the same selection (`album_pass.wanting` for the one ref: every rule of the pass holds, the keep itself being the "the server keeps it" clause), the same matcher (`album_finder.decide`) and the same write rule (`album_pass.commit_verdict`, in one transaction that reads the row again), with the length of the FILE just downloaded (`album_pass.file_or_listing_length`, the one definition that `length_and_source` calls too: the import's listing is 1 to 12 s off a file's own, N-11). **What it decides.** A song is filed under an album, tagged with the album, the track, the disc and the year with the release's picture embedded, and given a `cover.jpg` in the folder, ONLY from a `matched` answer. A song that has a real album keeps it (it is not asked and the album is never rewritten); `none` and `held` (`single_only`, `twin_held` and the other reasons) are remembered exactly as the pass remembers them and the song is kept where it is kept today, in `Singles` with no album, and the pass asks it again. **A catalogue that cannot be asked never delays or stops a keep** (down, resting, switched off, no answer within 10 s in all, the whole question included, a name with nothing to compare, no length): the keep goes on exactly as before slice 3 and NOTHING is remembered about the song for that reason (a name with nothing to compare, which costs no request, only forgets the placeholder literal, as the pass does). It costs one search per new keep of a song with no album, from the Host's address, as a background turn at the gate (an album's answer is cached for 7 days). **One planner, one tag builder, one folder picture.** `keeper.placement.plan_for_ref` and `keeper.tagging.tags_of` build a file's place and its tags from a ref (the keeper, the dry run and the repair of slice 5 all call them), and `keeper.covers.write_folder_picture` writes the folder's `cover.jpg` (shared with the cover finder): only inside `Encore/`, never over a `cover.*` or `folder.*`, only a catalogue picture (never a video's thumbnail), only in an album's folder (never in `Singles`). **Audit B-110, one file per ref.** `Keeper._existing` takes the song's OWN file first, wherever it lies (a `song_file` row of this ref with `source = 'youtube'` and a path under `Encore/` whose file is still on the disk, the preferred one first), and takes a file at the place it would choose now only when no other ref's row holds that path (compared without regard to case, like the music server); a library file (`source = 'library'`) is never taken as a kept one. The same rule is applied again after the download (`_finish`). **Not done here:** the extra copies the old behaviour already left on a Host's disk are not removed (a deletion has no undo and a stream may be in flight: the repair of slice 5 deletes them, one pass later and with its journal); no file already kept is moved or retagged (slice 5); a song that already holds a catalogue id and has no album is not asked (the pass does not ask it either); a song whose artist is a channel's name or nobody's is not asked; a song carrying the placeholder literal that is kept while the catalogue cannot be asked is filed in `Singles` and tagged with no album (the placeholder is never written into a file: `textnorm.is_placeholder_album`, in the planner and in the tag builder; the ref keeps the literal until the pass examines it). **The dry run** (`python -m encore_server.album_dryrun --new-keeps`, and a section "NEW KEEPS" in every report) shows, over a copy of a server's data, the folder each song the music server has no file of would be filed in, from the pass's selection (widened by the songs a keep is waiting for: a song played on two days has no like), the same matcher and the same planner; it measures those songs by the import's listing, because the file a keep reads does not exist yet, so its counts are a forecast.

**The Unicode pin (P2-25 slices 2 and 3; the advisor's rulings of 15 and 16 Nov 2026).** A stored key is a function of the Unicode data of the Python that made it: a title with one of the 622 CJK Extension I ideographs of Unicode 15.1.0 is a word there and a gap in 15.0.0. The fold is pinned to `textnorm.UNICODE_VERSION` (15.0.0 = Python 3.12 = the image's `python:3.12-slim`) and **the server REFUSES TO START on any other Python**: `create_app` and `python -m encore_server` do it first of all, before a folder or the database is opened, with a message that names the Python that is needed and how to get it (the image, python.org, `uv python install 3.12`); `keyrepair.repair` raises the same refusal; **the test run stops before its first test** (`tests/conftest.py`); `requires-python` is `>=3.12,<3.13`; `tests/test_unicode_pin.py` fails when the image, `server.yml` or `requires-python` moves alone. A Host who runs the Docker image notices nothing; a Host who starts the server by hand needs Python 3.12. There is **no environment variable, flag or setting that turns it off** (a Host who got past the message would store keys the next image cannot reproduce: the permanent drift the pin prevents). `python -m encore_server setup` and `backup` are not guarded: neither writes a key, and `backup` is a rescue tool. **Why a pin and not a table of our own:** `textnorm` uses `unicodedata` as an ALGORITHM (NFKC, NFD and NFC, `category`, `decimal`, case folding), not through a few look-ups, so a table of ours would be a copy of Unicode's normalisation and case-folding data: not feasible, and worse than the one Python ships. **What a Python bump costs** (and so the way out; there is no removal trigger, this is the permanent design): ONE pull request that (1) runs `tools/gen_text_fold_table.py` with the new Python (it refuses any other Unicode; it rewrites the phone's table and the fixture's digests; `--check` runs in CI), (2) raises `TEXTNORM_REVISION` (every install's keys are rewritten at its next start by the mechanism above, after its own copy), and (3) moves the image, `server.yml`, `requires-python`, `UNICODE_VERSION` and `UNICODE_OF_PYTHON` together. The developer's virtual environment is Python 3.12 for the same reason (`docs/guides/dev-gotchas.md`).

**After the migrations, at every start (`refmerge.repair`, N-11 part B).** Song refs that hold one file of the music server (the same `song_file.navidrome_song_id`) are one song that the old library scan made twice: the one whose file was attached first survives and takes everything the other had (likes, playlist entries, plays, imports, queued work, the songs of a saved release, the saved queue, the files merged key by key), then the other is deleted and a row of `ref_merge` remembers it. It runs before any thread starts, as one transaction after its own copy of the database (`/data/backups/encore-before-ref-merge-<time>.db`, kept, the path logged), changes nothing and takes no copy when there is nothing to merge, and a failure rolls back, is logged and does not stop the server. Pairs that name different source items (different video, ISRC or Deezer id), that one playlist holds both of, or one of which is on the key repair's worklist (`ref_recheck`: its file may belong to another song, reason `recheck_pending`) are **held**: never merged, written to the log at INFO on every start, and expected. It is code and not a migration because a migration cannot do it (the held pairs share a file for good, so a unique index on `song_file.navidrome_song_id` cannot exist, and the repair needs the survivor's rules).

**Song refs nobody points at are retired (`ref_janitor.py`, N-27 slice 2a, B-131, B-126).** A tap on a song the server cannot find leaves its `song_ref`; nothing ever removed it. Once an hour, as one more errand of the library link (after the finders), at most 500 refs a pass, a ref goes when ALL of this holds: no row of any person points at it (`song_file`, `playlist_entry` even a removed one, a `like` in `library_item`, `play_event`, `import_entry`, `saved_album_ref`, `work_item` that is still `queued` or `running`, `playback_state.ref` and the ids inside its `queue`, a survivor named by `ref_merge.into_id`), it has no live N-13 verdict (`missing.standing_of(...).live`: the window is kept so that the memory that saves a look-up at YouTube is not forgotten), none of its files changed in the last 14 days (`file_log`), and it is itself older than 14 days. "Nobody" means nobody among ALL the people: another person's like, entry or play keeps the ref for everybody. The refs go in ONE transaction; finished work goes with the ref by its cascade; the `file_log` rows of a retired ref go with it (no foreign key); `change_log` rows stay (they say "this was touched", the feed reads the state from the tables, so a phone that was away still learns a like was removed). It adds no column and no table. `tests/test_ref_janitor.py` compares the list of pointers with the schema (a table that names a ref and is not in `ref_janitor.POINTERS` fails CI) and shows each clause is load-bearing. It runs with the library link, so a server with no music server, or with `ENCORE_SCAN_EVERY_MIN=0`, does not run it. **A ref whose file was removed is retired like any other** (slice 2e): until then every ref that had ever held a file was kept, because the files feed can only list a ref that still exists and so could not tell a phone that was away that a song is gone; now every retirement leaves a tombstone (`ref_gone`, `17`) that the phone reads, so nothing is left to protect. A change of a ref's files in the last 14 days still keeps it (a file the music server lost an hour ago is not a song nobody wanted). The phone's half (a library row with no file, like, entry or download, absent from every feed page, older than 14 days) is slice 2b.

**The rows that kept a ref for ever are purged (`tombstone_purge.py`, N-31 = N-27 slice 2d).** A removed playlist entry and an `import_entry` counted as pointers and nothing ever removed them, so the songs of a deleted playlist and of every import stayed (VM 108: the 29 refs of a deleted test playlist). The janitor's rule is NOT changed; the reasons to keep a ref are removed after a time, by one more errand of the hourly library link that runs just BEFORE the janitor, at most 5000 entries and 50 imports a pass, in one transaction (a pass that fails changes nothing, a second pass changes nothing): a playlist entry removed more than 90 days ago, every entry of a playlist deleted more than 90 days ago, and the entries of an import that finished more than 60 days ago (its counts are stored first, see `import`). Fixed numbers, not Host settings. Then the janitor retires the refs nothing else points at (a like, a play, another person's entry or another import keep theirs) and `ref_gone` tells the phones. A phone that was away is still told: see `17` "Playlists and entries that are gone" and `34` CF-46. **Costs and limits, said plainly:** deleted playlist rows stay for ever (bounded by what people delete); an import whose matching never finished stays `running` and keeps its songs (a failed `match` does not end an import: not solved here); an `add_entries` retried with an entry id that was purged, by a phone that was offline for more than 90 days, would bring the entry back.

## 2. The phone's database (drift)

Drift, schema 7 (`app/lib/data/db/tables.dart`, `app/lib/data/db/app_database.dart`), additive migrations only: every shipped version has a frozen snapshot in `app/drift_schemas/` and an upgrade test that keeps its rows (`app/test/data/db/migration_test.dart`, `app/test/generated_migrations/`).
* **The Encore song references did not get tables of their own.** One `tracks` table carries both a plain music server's songs and an Encore server's song references: for a reference, `is_ref` is true, `id` is the ref id (`sr_...`, the same on every device) and `file_id` is the music server's id of the kept file when the server holds one (null: the song plays from the server's stream by ref); `video_id`, `artists_json`, `cover_url` and `explicit` carry what a catalogue song brings with it (schema 6). There is no `SongRefs` or `SongFiles` table.
* A like is `tracks.starred_at_ms` (saved albums and followed artists the same way on `albums` and `artists`); `pins` and `downloads` are keyed by the track id, which is the ref id on an Encore server; `playlist_entries` keeps the server's entry id and its fractional position next to the phone's own order.
* `outbox` holds the operation kinds of `17` section 5; `sync_state` holds the cursors of `library/changes` and `library/files` and the saved queue.
* **A song's artist link points at an artist the phone lists, whenever its album's artist is listed** (audit B-118). The music server lists only album artists in its artist index, and a song tagged `Post Malone, Swae Lee` belongs for it to an artist of that whole name that has no album and is not in the index; the song's `artistId` points at it, so the phone never receives that row (on a freshly signed-in phone: 382 of 4,719 songs, 145 such artists, 159 of the songs showing a single artist name because a reference carries its own first artist). `LibraryWriter.linkSongsToListedArtists` moves such a song to the artist of its album, after every write of songs and at the start of every sync run; a song with no such album keeps its link and the artist page then looks the artist up by name. A page of one thing the phone has no row for (artist, album, playlist) is never a bare spinner: after a moment it says so and keeps its Back.
* `albums`, `artists` and the rest of `tracks` are the browse index of the server's files. `requests` is the old homelab request portal (P2-07 removes it).

## 4. The migration (task P2-11, runs once per server when the new Encore server first starts next to Navidrome)

1. **Back up** Navidrome's database, the people service's data folder and the fetch service's work folder (to `/data/backups/`).
2. **People:** every Navidrome user except the hidden administrator becomes a `person`; roles and "invited by" come from the people
   service's data.
3. **Files:** scan the libraries Navidrome knows; every song gets a `song_ref` (matched by ISRC/MBID tags if present, else `norm_key`)
   and a `song_file`. The same recording found in several per-person folders becomes **one ref with several files**; the duplicates
   report (`19` §6) lets the Host delete extra copies later (D-2: one copy per song). New keeps go to `/music/Encore/`.
4. **Likes, playlists, plays:** read per person from Navidrome. Preferred: through the gateway's trusted header acting as each user
   (experiment X-2); fallback: each phone uploads its own library on its first launch after the update (P2-02). Navidrome play
   counts and scrobble history become `play_event`s, so Year in Music continues.
5. **Running imports:** finished ones become playlists of refs; unfinished ones are re-created as imports of refs (their list is in
   the work folder) so nothing waits for downloads anymore.
6. **Check:** counts per person (likes, playlists, entries, plays) before and after are printed; any difference stops the switch.
7. **Switch:** the app talks to the new server only after the check passes; the old services stop (not deleted) for 14 days.
* Proof (when P2-11 is scheduled): run it first on a copy of a real old install on the test VM 108; only then on anybody's server, with their go and a backup first.
