# 17 — The app ↔ server contract (API, live channel, sync, errors, versions)

Why this page exists: `tasks/P2` had only an endpoint sketch. Without fixed conventions every agent invents its own error format,
ids and retry rules, which is how the old project got six services with six habits. Everything here is binding for the Encore
server and every client (Android now, web/PC later). The machine-readable form is **planned, not built**: an `openapi.json` written into the repository
by the server and checked by a server test (`11` ADR-R41 T5). Today there is no such file and no such check, and since S1 (B19) the running server no longer serves `/openapi.json`.

## 1. Conventions

| Topic | Rule |
|-------|------|
| Base | One origin per server; all Encore routes under `/encore/api/v1/…`; the live channel at `/encore/live`; audio at `/encore/stream/…` |
| Auth | `Authorization: Bearer <device token>` (P3-03). **Target, not what the app does yet:** the app still signs its ordinary Encore calls with the music-server login as `u`, `t`, `s` in the URL query (`31` D-1, `app/lib/data/encore/encore_api.dart`); only the live channel uses the device token, and the server accepts both (P2-20 slice 3 and the Bearer-token move are RC2). Never in the URL, except audio URLs, which use a signed `?sig=` (6 hours for a song address, 7 days for a cover address: `auth.py` `STREAM_URL_TTL_S`, `COVER_PASS_TTL_S`) because players cannot set headers everywhere |
| Ids | Server-made ids are opaque strings with a type prefix: `sr_` song ref, `pl_` playlist, `pe_` playlist entry, `dv_` device, `im_` import, `jm_` Jam. Clients create ids for things they create (`pl_`/`pe_` as ULIDs) so an offline create can be retried without duplicates |
| Time | All timestamps are UTC milliseconds from the server clock (`at`); the server returns `serverTime` in every response so clients can measure their clock offset |
| Writes | Every write is **idempotent**. Today that holds because each operation is meaningful on its own (a like is a set member; a playlist create and an entry add carry ids the client made, so a retry is a no-op: `create_playlist` and `add_entries` in `library.py`). **Target, not built:** an `Idempotency-Key` header (a ULID per user action) that the server remembers for 7 days; the table `idempotency_key` exists (migration 0001) and no code reads or writes it (register B-44, B-63; P3-29 decides whether to build it or drop the table) |
| Lists | Cursor pagination: `?limit=` (max 500) and `?cursor=`; responses `{items, nextCursor}` |
| Changes | `GET /library/changes?since=<cursor>` returns everything changed for this person since the cursor, including deletions (tombstones), in order |
| Errors | One shape everywhere: `{"error": {"code": "song_unavailable", "message": "This song isn't available in your country.", "retryable": false, "retryAfterMs": null, "details": {}}}`; `message` is a plain sentence the app may show as is; `code` is for logic |
| Rate limits | `429` with `retryAfterMs`; per person and per device |
| Versions | `GET /encore/api/v1/info` → `{apiVersion: "1.0", minAppVersion: "0.1.0", serverVersion, features[]}` (today's values); additive changes bump the minor; a breaking change is a new `/v2` while `/v1` keeps working for **two app releases**; the app refuses to run against a server whose `apiVersion` major it does not know and says "Update Encore" (or "Ask the owner of <the server's name> to update the server", with no person's name: `design/03`, designed, not built). `info` lists `features[]`: a server that keeps songs adds `keep` (`refs/{sr}/keep`, `keep/progress`, `keep/watch`, `keep/retry`) and `keep-ask` (`keep/ask`); every server lists `unavailable-ids` (`POST refs/unavailable` takes ref ids, B-128); a server whose Host has not switched the catalogue off lists `catalogue` (the routes under `catalogue/`, P2-12); **an app does without a feature the server does not list and never tries a route to find out**. `info` also carries `youtube` and `catalogue` (each `{state: ok|resting|off, resumesInSec}`) and, on a server that keeps its own yt-dlp fresh (ADR-R39), `tools: {ytDlp: {running, pending, state: ok|degraded}}`: `pending` is a newer version that waits for a quiet moment to be switched to, `degraded` means songs from YouTube are not working right now. Built (ADR-R40, decided 2026-10-23): `info` always carries `serverId` and `publicKey`, and `GET /info?challenge=<nonce>` adds a signature over the nonce and the id (`identity.py`); a signed-in `GET /encore/api/v1/server` returns `{serverId, name, addresses: [{kind: home|away, url}]}` |

## 2. Error codes (the closed list; new codes need a doc change)

`unauthorized`, `forbidden`, `not_found`, `conflict` (stale revision), `validation`, `rate_limited`, `song_unavailable`
(`details.reason`: `not_found` | `region_blocked` | `age_restricted` | `removed`), `source_busy` (YouTube pushing back; retryable),
`source_unreachable`, `storage_full`, `server_busy`, `upstream_timeout`, `federation_disabled`, `peer_unreachable`, `internal`.
`server_busy` is also the answer (503, retryable, "The music server is not answering just now") when the music server gives no answer to a login check (it is down, restarting or sent an error page): never `unauthorized`, never counted as a wrong guess, nobody is signed out (AUDIT B-41). Only a refusal by the music server itself (Subsonic error 40 to 44) is `unauthorized`.
Each has one plain message, owned by the server (`server/encore_server/encore_server/errors.py`; English only today), so all clients say the same thing.

**Signed addresses (`/encore/stream/{sr}`, `/encore/cover/{id}`).** The query values the server gives (`p`, `e`, `sig`) are written into an address **exactly as given**. The signature covers `e` (whole seconds of the **server's** clock), so a client never works it out again from its own clock: a phone one second out had every picture refused (audit B-115). The phone's clock decides only when to ask for a new ticket, and a `401` on a signed address means "ask for a new ticket" (the picture ticket is replaced once, never in a loop). Covered by `signed_addresses_test.dart` (a skew table).

**The catalogue (P2-12 slice 1, built, not walked; nothing in the app calls it yet).** The routes under `catalogue/` answer a signed-in person from Deezer's public catalogue, **through this server** (one gate, one cache, one shape: `11` ADR-R47), so a client never talks to the catalogue itself (ADR-R38). **No read here makes a song ref, a row or a file** (B-126, B-131: the page of a catalogue is not a song on this server); a song is made by a person's tap, through `POST refs/resolve`.

* `GET catalogue/search?q=&types=artists,albums,tracks&limit=8` (`q` 2 to 200 characters; `limit` 1 to 25, for albums and songs: artists are always 8) answers `{query, artists, albums, tracks, unavailable?}`: only the kinds asked for. A kind that could not be asked is named in `unavailable` (and its list is empty), the others are still there; **a kind that could not be asked is never an empty list that means "nothing found"** (B-124). At most 3 outside requests (the ceiling of one search is 7, for the forgiving and artist + title reading of later slices).
* `GET catalogue/artists/{id}?parts=popular,releases` answers `{artist, popular?, releases?, unavailable?}`: who the artist is, its ten most popular songs, and what it released **newest first with the editions of one release folded** (the explicit and the clean one, "Deluxe Edition", "Remastered 2011": the newest stands for the release; the rule is the phone's own `normalizeForMatch`, in every script, and a title with no letter or digit is never merged with another). The list of releases names no artist of its own in Deezer's answer: each carries the page's artist. At most 3 outside requests.
* `GET catalogue/albums/{id}` answers `{album, tracks, unavailable?}`: the album, then its songs in order (`trackNo`, `discNo`; the songs name the album and its cover, which Deezer's own list of an album's songs leaves out). A missing album asks for no songs. At most 2 outside requests.
* `GET catalogue/genres` answers `{genres: [{id, name}]}` (no outside request: the list is this server's) and `GET catalogue/genres/{id}` answers `{tracks, artists, albums, unavailable?}`, what is on top in the genre (`0` is the whole catalogue).

**Shapes.** An artist `{id, name, picture, fans, albumCount}` (a list that has no fan count, as a genre's, says `null`); an album `{id, title, artists: [{id, name}], cover, trackCount, year, releaseDate, recordType}`; a song `{id, title, artists: [{id, name}], album: {id, title} | null, cover, durationMs, isrc, trackNo, discNo, description}` where **`description` is the object `POST refs/resolve` takes** (made here and only here, so a client no longer builds it): it carries `isrc` and `deezerId` (text) and **never a `videoId`** (B-86: a video a client names would override the title and artist). `artists` is a list from the start, so that several credited artists change no shape (F13). A picture field (`picture`, `cover`) is the catalogue's picture host's address or `null`, **never an address at `api.deezer.com`** (it redirects and tells Deezer who asked) and never the grey silhouette Deezer gives an artist with no picture of its own; the phone still loads those pictures from the picture host until a later item serves them through the server (PRIVACY.md). Ids are Deezer's, **as text, digits only**; an id that is not digits is refused (`validation`) before it reaches an outside address. **Convention (B-89): a catalogue id has no prefix when it is Deezer's; another source's ids will carry one (`ytm:`). A saved album is stored as `cat:<catalogue id>` by the app when it came from the catalogue; an album of the music server's own library is stored under the music server's album id** (the prefix is the app's, the server does not check it yet: B-89 stays open for `PUT saved-albums/{id}` refusing anything else, and for `18`).

**Errors** (the closed list): `validation` (a search under 2 or over 200 characters, a `limit` outside 1 to 25, an unknown kind or part, an id that is not digits), `not_found` (`details.reason` is `not_in_catalogue` for a thing the catalogue does not have, remembered for 5 minutes and **not** a sign that the catalogue is unwell; `catalogue_off` on a server whose Host switched it off), `rate_limited` (30 outside requests a minute for one person; a cached answer and a call that joined another's request cost none), `source_busy` (503, retryable: the catalogue could not be asked at all; `retryAfterMs` says when it is let through again, and `info.catalogue` says `resting`).

**The gate, the cache, the switch.** Every outside request of the server to Deezer (these routes, the cover finder, the artist finder, the keeper's cover) takes a turn at one gate: 20 requests in 5 seconds after a burst of 6, at most 4 in flight, a person's request before background work (which keeps 250 ms between its own), single flight per outside request, and a rest of 30 seconds, doubling to 10 minutes, after a refusal (429, 5xx, Deezer's own "Quota limit exceeded" in an HTTP 200 body) or three timeouts in 30 seconds; the first request after a rest is the one trial. Answers are remembered in `catalogue-cache.db` in the data folder (not `encore.db`, not in the backup, safe to delete: at most 20,000 answers or 50 MB), one outside request per entry, under a hash of the request: a search 15 minutes, an artist or its popular songs 24 hours, its releases 6 hours, an album and its songs 7 days, a genre's chart 6 hours, an empty answer 5 minutes; **a catalogue that could not be asked is never stored**, and while it cannot be asked an answer up to 30 days old that holds something is served instead (an empty one never is). `ENCORE_CATALOGUE=0` opens no connection to the catalogue at all: no feature is listed, the routes answer `not_found` (`catalogue_off`), the finders skip their pass without remembering a miss, and no cache file is made. The cover finder and the artist finder ask through the gate, not through the cache.

**Songs merged into another (N-11 part B).** The server repairs, at start-up, the songs the old library scan made twice (`18`): one ref survives and the other no longer exists. Three things are contract:

* **An old id keeps working.** Every route that takes a song id from a client (`GET refs/{sr}`, `likes`, `playlists/{pl}/entries`, `plays`, `PUT playback` (its `ref` and `queue`), `refs/{sr}/keep`, `refs/{sr}/stream-url`, `refs/prepare`, `saved-albums`, and a signed `/encore/stream/{sr}` address issued before the repair) accepts the id of a merged-away song and acts on the survivor; `GET refs/{old}` answers with the survivor (its `id` is the survivor's), and what is stored is always the survivor's id. A song described again (`POST refs/resolve`) the way a merged-away one was (its ISRC, catalogue or video id, or artist + title + a length within three seconds of the deleted ref's) finds the survivor and makes no ref.
* **The phone is told about the merge through the files feed**, with a cursor of its own (not `cursor`, which counts changes of files): `GET library/files?since=&limit=&mergesSince=` answers `{refs, cursor, more}` as before and, when `mergesSince` is sent, also `merges: [{"from": "sr_...", "into": "sr_...", "seq": 7}]` (the ids in `from` no longer exist; `into` is the survivor, a live ref), `mergesCursor` (the `seq` to send next time) and `mergesMore` (true while the next page, of the same `limit`, has more). `mergesSince=0` returns all of them, so a phone that updates months later still learns every merge, in order (a survivor that was merged in turn appears as a later row). Without `mergesSince` the answer carries `merges: []`, `mergesCursor: "0"` and `mergesMore: false`: an app from before merges is sent nothing it does not read. A phone folds its own copy of `from` into `into` (downloads, star, places in playlists and in the saved queue); the server has already moved its own copies, and `library/changes` re-sends every like and entry that now names the survivor.
* **A real response is a fixture.** `app/test/fixtures/server/library-files-with-merges.json` is written by the server's own test (`server/encore_server/tests/test_ref_merge.py`, on synthetic data, with `ENCORE_WRITE_FIXTURES=1`) and that test fails when the answer changes; the app's parser must read it. (There is no `openapi.json` and no schema test yet: ADR-R41 T5 is "planned, not built", see the top of this page.)

## 4. The live channel (`/encore/live`, websocket)

* One connection per running app; authenticated by the device token in the first message; the server sends `hello {serverTime,
  cursor}`; ping/pong every 25 s; reconnect with jittered back-off (1, 2, 4 … 30 s); on reconnect the app calls `library/changes`
  and `GET playback`, so no event is ever needed to be correct (events only make things faster). The server ends a connection whose device is signed out, revoked,
  locked or removed: it closes the socket with code **4401** within a moment (built, S3 B5: `live.py` `Hub.end`), and the app takes 4401 as "token refused" (`31` CN-23).
* Events (server → app): `library.changed {cursor}`, `playback.changed {state, rev}`, `device.takeover {by}`, `device.command
  {command, rev}`, `device.state {dv, state}`, `import.progress {im, counts}`, `keep.progress {groups, youtube, serverTime}` (to the device that watches, `keep/watch`), `jam.state {…}`, `friend.request {…}`,
  `activity {…}`, `server.notice {code, message}`.
* Messages from the app on the socket are only `device.state` reports and Jam clock pings; everything else goes through HTTP (one
  write path, idempotent, easy to retry).

## 5. Sync and conflicts (offline edits on several devices)

* The phone keeps an **outbox** of operations, not snapshots: `like(sr)`, `unlike(sr)`, `addEntries(pl, [sr], after)`,
  `removeEntries(pl, [pe])`, `move(pl, pe, after)`, `rename(pl, name)`, `deletePlaylist(pl)`.
* The server applies operations in arrival order; each is meaningful on its own, so two devices' offline edits **merge**: adds from
  both survive; a removed entry stays removed; a move of a removed entry is dropped; renames are last-writer-wins by server arrival;
  operations on a deleted playlist are dropped and reported (`conflict`) so the phone shows "That playlist was deleted on another
  device".
* **Songs the server cannot get (N-13).** The server remembers, on the song's ref, a "no" that the source ANSWERED: `not_found` (the search answered and nothing acceptable matched), `removed` (the upload is gone, and one search for another upload also found nothing) and `age_restricted` (the only copy needs an age check; its own reason so that a sign-in option could clear those without voiding the others). **Never remembered:** anything that may pass (YouTube refusing or resting, a timeout, the network, a search that could not be made: `search_failed`, a 502 `source_unreachable`, B-122, a file too big). The memory is believed for **7 days from the last real try** (`missing.WINDOW_MS`) and only if the matcher that made it is the one running (`MATCHER_REVISION` in `sources/youtube/scoring.py`: raise it when a change could make the matcher find what it did not, and every older "not found" is void at once). Inside the window a tap, a prepare, a keep and an import match all refuse at once with the same answer a fresh "no" gives (a `GET /encore/stream/{sr}` is the usual `404 song_unavailable` with its reason) and **make no look-up at YouTube**; after it nothing is shown, and the next person's tap does one real search, which clears the memory (found) or starts a new window. There is no background sweep. A stored upload that turns out to be gone is not a reason by itself: one search for another upload comes first (the dead id stays in the ref until a live one replaces it, so that the next description of the song, which carries the same dead id, does not void the memory), and only an empty search stores `removed`. The memory is cleared when the song is found: a file is attached, an upload is remembered where there was none, a description names one where there was none. It is not kept, and not believed, while a test fault is injected (`ENCORE_FAULT`). A merge (N-11) never hands it to the survivor. **How a phone learns, two ways, both optional so that an older server and an older app keep working:** (a) a ref carries `unavailable: {reason, message, since, retryAfter}` (milliseconds; `message` is the server's own sentence, the one the stream answers with) **only while the memory is believed and the server has no file of the song**; absent otherwise (not `null`). The memory is **not** written to the files feed (`GET library/files` is the phone's index of what the server keeps; a song with no file is not its business). A row of the phone's own library is therefore asked about by its ref id (b), not read from a feed. (b) `POST refs/unavailable` takes **either** `{"songs": [described as refs/resolve takes them]}` **or** `{"ids": [ref ids]}` (never both; 1 to 100; ids are texts) and answers `{"items": [...]}` in the same order: `null` (no known problem, a song never seen, an id no ref has, a song the server keeps (it has a file), or one that cannot be read) or the object above. A Search or an album is catalogue songs, which have no ref on the phone, so they are described (`songs`). **The rows of the phone's own library are refs** (the song somebody tapped is one from then on, with no file; a playlist entry or a liked song may be one too), so the phone asks about them by id (`ids`, B-128: the exact identity, no description to match; an id that was merged away (N-11) answers for its survivor). **It is a read:** it makes no ref and asks YouTube nothing, so a phone asks once per list it shows, after the rows are drawn, only for the rows that have no file and are not downloaded, and never while the server is away or on a plain music server. **Versions:** `info.features` lists `unavailable-ids` on a server that takes `ids`; an app never sends `ids` to a server that does not list it (an N-13 server from before B-128 answers it 400), and reads a 400, 404 or 405 as "no verdicts" too. A server that has not got the route at all answers 404 or 405 (the route `GET refs/{sr}` matches the path): the app reads that as "no verdicts", never as an error. **When a song is refused for good** (a stream answers `404 song_unavailable`, or a tap finds the ref marked) the phone does not copy the window from the answer (the 7 days are the server's rule, and the body carries only the reason): it asks again at once and shows what the server says; an older server that remembers nothing gives no mark.
* **Preparing the next songs (P1-04, audit B-107).** `POST refs/prepare` takes `{"ids": [song ids]}`, one to three, and answers at once `{accepted: n}` (the same song once, a song the server does not know not at all, `0` when this server cannot fetch songs from YouTube). The player sends the next two songs of its queue when the current one is audible; the server does what a play does up to the first byte (the song's upload and its stream's address, kept for most of an hour, no bytes), so a Next to that song finds both and its first bytes arrive after 0.1 s instead of 2.0 to 2.3 s. It is background work (kind `prepare`, interactive pool, one item per song however many people want it): it waits its turn at the background pacer, asks nothing while YouTube is being given a rest, nothing for a song the server keeps or already has the address of, and at most 40 songs an hour (only songs that really ask YouTube count, so listening in order, where the second song ahead was prepared a song ago, uses about one slot a song); what does not happen is not retried and not reported (the song is then looked up when it is played, as before). A web client calls it the same way.
* **Saving a release (D-21, decided by the advisor 2026-10-30).** On an Encore server "Add to library" and "Download" on a catalogue release are server operations, and the screen shows only what the server confirms. `PUT saved-albums/{id}` takes an optional body `{"refs": [song ids]}` (at most 500; the ids the phone got from `refs/resolve`). One call: the save is recorded (the change feed delivers it), and the server **keeps those songs in the background, first in line, whether or not the phone stays** (the thin-client rule: a web client needs the same). All or nothing: a song the server does not know refuses the whole call, `404 not_found`, "That song is not known to this server." with the id in `details`, and nothing is saved. Safe to repeat: the second call changes nothing and queues nothing twice (a song whose keep failed is asked for again). The answer is `{changed, cursor, keep: {songId: {state: queued|keeping|kept|failed|none|unavailable[, reason]}}}`, the states of `GET refs/{id}/keep`. **`reason` is a sentence for the one who asks, never the raw text the keeper stored** (that can name an exception, a file or a folder): for a failed song, the Host reads the cause and anybody else the plain fact (the same sentences as `keep/progress`); for a song that waits, "YouTube is resting.", "YouTube is not answering.", and for a full disk the Host reads "The server's disk is nearly full, so nothing more is kept for now." and a member "The server has no room for now."; a wait with nothing a member can use ("Something went wrong, trying again: ..." is the Host's) has no `reason` for a member (`keeper/failures.py`, `describe_wait`). A download is this call plus a pin on the phone, written at once so it survives the app being killed. Likes stay likes: saving an album never fills Liked Songs.
* **Keep progress (P2-22 part 1, built 5 Nov 2026, decided by the advisor).** A phone that downloads a 200-song playlist shows two numbers, **both always** (`33` PB-35): how many songs are on the phone (the phone's own downloads table, **never sent to the server**) and how many the **server has ready**. `POST keep/progress` is the second number for everything the person pinned, in one request (a call per song would be hundreds for one screen). Request: `{"groups": [{"kind": "playlist" | "release" | "liked", "id": "...", "refs": [song ids]?}]}`, 1 to 50 groups, ids as the server knows them (a playlist's `pl_…`, a release's catalogue id as it was saved, anything for `liked`). `refs` (at most 500) is only for a release **saved before this version**, whose songs the server did not store: it is used when none are stored, and only songs the server knows count (a release saved now stores its songs with the save, `PUT saved-albums`, and a removed release forgets them). Answer: `{"groups": [{kind, id, total, ready, keeping, queued, failed, retryable, failures: [{ref, title, artist, reason, retry}]}], "youtube": {state: off|ok|resting, resumesInSec}, "serverTime"}`, in the order asked.
  * **Every song of a group is in exactly one bucket, so `ready + keeping + queued + failed == total`** (a song twice in a playlist is one; a removed entry is not wanted). `ready`: the music server holds a file of it, **including songs that are also on the phone**. `keeping`: being fetched now. `queued`: waiting its turn, **including the wait for YouTube's rest** (`youtube.resting` and `resumesInSec` say how long; a song waiting for the rest is not failed). `failed`: the server gave up, **or has no record of ever trying** ("The server has not fetched this song yet.") **or kept it once and no longer has the file** ("The server no longer has this song's file."): all three are wanted songs the server does not have, so the phone names them and offers Retry. **Changed from the first decision, which called a finished item without a file `keeping`:** that would show "fetching" for ever. It is safe to call it lost because the keeper attaches the file before it marks the item done, and the answer reads the queue before the files, so a song seen finished is already linked when the files are read. **Against `GET refs/{sr}/keep`:** that call says `none` for a song that is finished without a file, cancelled or never tried (it is what `PUT saved-albums` and `POST refs/{sr}/keep` re-ask on, and stays so); in the batch `none` of a **wanted** song is `failed` (a test walks all seven situations through both). A failure is no longer forgotten with the scheduler's cleanup of old work while somebody still has the song (liked, in a playlist, in a saved release): it is the reason the phone shows.
  * `failures` names at most 20 songs per group (the first, in the group's order); `failed` always counts all of them and `retryable` counts those where asking again can work. `retry` is false for what will not change however often it is tried (not found, no copy, an age check, too big, too long, not in the music folder). **`reason` is one short sentence and depends on who asks:** the Host (role `owner`) reads the cause ("No upload of this song was found on YouTube.", "The only copy on YouTube needs an age check, which this server cannot pass."), a member the plain fact ("Not found.", "Needs an age check.") and never a word about the server's setup or a path (`keeper/failures.py`; a test keeps every reason the keeper can give up with in step with a sentence).
  * **A group the person cannot see is left out of the answer, exactly as one that does not exist** (another person's playlist, a deleted one, a release not saved, an unknown id): the three answers cannot be told apart, so no id can be probed. Only the person's own playlists exist for this call (sharing a playlist is not built, `34`). A server that does not keep songs (no `keep` in `info` `features`) answers `404 not_found`, "This server does not keep songs."; the app does not call it then and shows no server stage. Asking changes nothing: a wanted song nobody fetched is reported, not started; **Retry is its own call, `POST keep/retry`.**
  * **The push (part 1b, built 5 Nov 2026).** `PUT keep/watch {"groups": [...]}` (the same groups as `keep/progress`; **an empty list stops watching**; only a signed-in device, one with a device token, because it needs a live connection to be told on) says which downloads this device watches and **answers with the current answer, exactly like `keep/progress`**: a phone that has just connected needs no second call. From then on the server pushes `{"type": "keep.progress", "groups": [...the same objects...], "youtube": {...}, "serverTime"}` **to that device only** when the answer changes, **at most once every 2.5 s**, never the same answer twice. The pushed answer is produced by the same code as `keep/progress` (called as that person, with the Host's or the member's sentences as they are at that moment), so a group the person does not have never appears in it. YouTube's count-down is not news: only a rest that starts, ends or moves by more than half a minute is pushed. **No event is ever needed to be correct (section 4):** the watch lives in memory; **a phone says what it watches again on every reconnect and gets the current answer in the reply**; a watch whose device has been disconnected for 5 minutes is forgotten.
  * **Retry (P2-22 part 4, built 5 Nov 2026): `POST keep/retry {"kind", "id", "refs"?}`**, ONE download (the same naming as a group of `keep/progress`). It asks the server again for the songs of that download that are `failed` **and where asking again can help** (`retry` true: a song nobody fetched, a file that is gone, a try that failed for a reason that may pass), the same way `PUT saved-albums` and `POST refs/{sr}/keep` ask: kept for the person who pressed it, **first in line**. A song YouTube does not have, an age check, a too-long or too-big file are left alone. Answer: `{"retried": n, "group": {...as keep/progress gives it now...}, "youtube": {...}, "serverTime"}`. Pressing it twice is harmless (the second finds nothing failed: `retried` 0). A download the person does not have is `404 not_found`, "That download does not exist (any more).", the same answer as one that does not exist (nothing is started for a download that is not theirs); a server that does not keep songs answers `404 not_found`, "This server does not keep songs."; a request that is not one known download is `400 validation`.
  * **Ask (P2-22, B-62, built).** `POST keep/ask {"groups": [...]}` is what **pressing Download on a playlist, a release or the liked songs does** (the groups are those of `keep/progress`, 1 to 50). For the groups the person has it asks the server for every song it does not have yet **and is not already fetching**: the ones waiting in the queue move up, and the ones nobody queued (never tried, cancelled, kept once and the file is gone) are queued. **A song whose keep has failed is NOT asked again by this call, only by `keep/retry`** (the Retry button): a phone says what it wants again every time it connects, and asking must never be what tries a failed song again at each start of the app (it would hit YouTube from the Host's address for ever). Answer: `{"asked": n, "groups": [...as keep/progress gives them now...], "youtube": {...}, "serverTime"}`. **Priority:** a tap on one song (`POST refs/{sr}/keep`) goes ahead of everything; a whole download asked for at once (`keep/ask`, `keep/retry`, saving a release) goes ahead of other people's imports and background work but **behind any tap** (`scheduler.PROMOTE_MANY`), because the queue looks at its first 200 items before it shares the turn between people (B-39, P3-32): a 500-song download at the level of a tap would stand in front of the next person's tap for as long as it lasts. A promotion only ever raises, and a download **never ends a pause before a retry** (the scheduler's back-off after a hiccup, YouTube's rest, a full disk): only a tap on that one song does. **Safe to repeat** (Retry, a reconnect, a second phone): nothing is queued twice and a repeat changes nothing (measured in-process, 2,000 liked songs: the first call 90 ms, a repeat 58 ms and no write to the queue). A group the person does not have is left out of the answer, exactly like `keep/progress`, and nothing is started for it. **`keep/watch` never asks** (telling a phone how it goes changes nothing). A server without `keep-ask` in `features` is simply not asked: the songs wait their turn in the background as before.
* Likes are a set; like/unlike conflicts resolve by **arrival order at the server** (decided 2026-10-23, `34` G-1: with a live connection two phones of one person see the real order within about 2.5 s; the like's own time only keeps the order of Liked Songs). Every pair of operations, with its test, is in **`34`**.
* Playback state uses `rev` (optimistic concurrency): a write with an old `rev` gets `conflict` and the current state.
* Journey **J-15** (`14` §3) is the acceptance test.

## 6. What the phone stores (and what it never needs the network for)

The phone mirrors the person's library (refs it uses, likes, playlists, saved albums, follows, history for Year in Music), the
covers it has shown (bounded cache) and everything downloaded (never evicted). It does **not** mirror the server's whole catalogue;
search of songs not in the person's library needs the server.

## 7. Timeouts and retries (one table for every client)

| Call | Timeout | Retry |
|------|---------|-------|
| Any read (library, info) | 8 s | 3× with back-off, then show the cached data quietly |
| Writes (outbox) | 15 s | forever with back-off (outbox), stop on non-retryable codes |
| Search | 3 s | none (the next keystroke retries) |
| Catalogue routes (`catalogue/*`) | 4 s on the phone; the server answers inside 2.5 s (2.0 s per outside request, 1.0 s to connect) and says which part it could not ask | none (a cached answer or the next visit retries) |
| Stream start | 10 s to first audio byte | 1 retry, then the plain error |
| Live channel connect | 10 s | back-off up to 30 s, forever while the app runs |

**Target, not built (register B-74).** Today the Encore client is one `Dio` with a 6 s connect timeout and 30 s send and receive timeouts for every call (`app/lib/app/session.dart`, `_buildDio`); there are no per-call classes and no three-fold retry of reads. The outbox's own back-off (20 s doubling to 30 min, `34` CF-5) is real.
