# 36 — Two doors, the helper on the server computer, and the admin site (P3-21, P3-25, the architecture of P3-06)

> **In short.** D-61 says every Host action is a button AND a command, both first-class. This document says how, in engineering terms, so that the pages, the installer and the `encore` command are built once and cannot disagree. (1) An action is one function in the server (an *operation*); the admin API route and the `encore` command are two thin doors onto it. (2) The admin pages are a **plain static client of a JSON admin API** (no build step, no framework, no cookies): the same API serves the later web player and an in-app Host page. (3) A page may never hold the computer (P3-04), so update, back up, restore and the away address go through a **small helper on the computer with a fixed list of actions**, reached by a local socket and nothing else (§3). (4) The button installer is, for the first target (the owner's Proxmox homelab), a **ready-made server image** built by running the very same `install.sh` in CI, so both doors make the same installation and one proof covers both. (5) What the roadmap's coming features need from the server is listed in §8; where `main` falls short is an item on the board, not a sentence here.

Read first (do not redo): `15` (every page, on paper), `35` (add-ons: the manifest and the settings store), `22` (updates, backups, moving), `21` §3–§4 (who can reach what), ADR-R7 (the installer options were weighed), ADR-R25 (away from home), P3-04 (no Docker socket in the web-facing server), P3-16 (a forgotten password), P3-27 (a release channel).

## 1. One operation, two doors

```
 button on a page ──► POST /encore/api/v1/admin/...  ─┐
                                                       ├──► operation (server/encore_server/encore_server/ops/<name>.py)
 `encore <command>` on the computer ──► the same ─────┘        │  needs the computer? ──► the helper (§3)
                                                               └─ writes the log line and the job record
```

* An **operation** is a plain function with typed arguments and a typed result, no web and no terminal in it (`ops/backup.py`, `ops/update.py`, `ops/addon.py`, `ops/people.py` ...). It checks its own preconditions in words ("a backup is already running"), writes one audit line (who, what, when, the result in a sentence, never a secret), and returns a result a person can read.
* The **route** calls it for the signed-in owner; the **command** calls it through `docker compose exec encore-server python -m encore_server op <name> --json '{...}'` (so the Host's terminal and the page run the same Python on the same database), or, for the operations that need the computer itself, asks the helper directly (it must work when the web server is down: `encore update` is exactly what a Host runs when the server does not start).
* **A test makes the two doors equal**: for every operation, a table test calls the route and the command with the same arguments on a fake helper and asserts the same result, the same audit line and the same refusal sentences. An operation with a door missing is a failing test, not a review comment.
* **Long operations are jobs.** A route that starts one returns `{"job": "jb_..."}` at once; `GET admin/jobs/{id}` returns `{state, steps: [{words, done}], result}`; the live channel also pushes `admin.job` to the owner's devices. The job's truth for an update lives in a **file written by the helper** (`/opt/encore/jobs/<id>.json`): during an update the server is restarted, so a page that asked the server alone would lose the job. After the restart the new server reads the same file, and the page, which polls and retries until `GET info` answers, shows "Updated to 1.3" or "Rolled back to 1.2: the new version did not start" (the sentence of P3-14).

## 2. The admin site

**What it is.** A set of static files shipped in the image (`server/encore_server/encore_server/web/`: one HTML file per page, one small JavaScript module per page, `tokens.css` generated from the app's design tokens by `tools/gen_admin_tokens.py` as the old admin did, Figtree as the font file already in `legacy/`). No build step, no package manager, no framework, no outside request (no font service, no analytics): a stranger's installation works with the internet unplugged. The pages are what `15` §2 and §4 draw; the old site in `server/legacy/encore-admin` is a **source of copy and tests, not code to run** (it was a separate service that called Docker; its `redact.py` rules and `test_*_page.py` cases are ported).

**The API comes first.** Every page does nothing a route does not already do: `/encore/api/v1/admin/*` and, for the first run, `/encore/api/v1/setup/*` (tables in `17` §3, group "admin"). The routes are owner-only, documented, tested by themselves and consumed by the page, by `encore` and, later, by the app's Host page: a screen can change without a server release, and a second client costs no server work (ADR-R38: clients are thin).

**One session model, decided once for the admin pages and the web player (P6-02).**

| Option | For | Against | Verdict |
|--------|-----|---------|---------|
| A. **The device token in `sessionStorage`**, sent as `Authorization: Bearer` (what every client already does) | No new way in: nothing in `get_principal` changes; no cookie, so no CSRF class at all; the browser is one more device in "my devices" and is revoked from there, from the phone too; the web player (P6-02) keeps the same bearer token and the same signed addresses | A script that runs on the page could read it | **Chosen**, with a strict CSP (below) so no foreign script runs, and a **browser session**: the page signs in with `deviceKind: "web"` (a field of the sign-in that already exists and already makes a device of kind `web`), and the server ends such a device after 12 hours unused and 7 days in all (`get_principal` and the live channel both check it), while the page keeps the token only for the life of the tab |
| B. An `HttpOnly` `SameSite=Strict` cookie | Not readable by script | A second authentication path on *every* route (a cookie then authorises the whole API), CSRF protection to build and keep, cookies on a server reached by IP, name and tunnel | Rejected: more attack surface than it removes while the CSP exists |
| C. A "remember this browser" token in `localStorage` | Convenient | Survives the tab; a stolen laptop is a signed-in server | Not now. If asked for, it is a separate, revocable, owner-visible device kind |

**What the expiry is, and is not.** The device kind is the client's own word, so the limit protects a forgotten tab and an old session of a stolen laptop; it is **not a boundary against somebody who holds the password** (who can sign in again, or sign in as a phone). The sign-in itself sends the password over plain HTTP when the page is opened by its home address: that is the accepted risk of `21` §4 (the same sign-in as the app's, once, then a device token; H30), and the page is never reachable on the public address.

Every page of the **admin site** is sent with `Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, `Cache-Control: no-store` for pages that show anything. **No inline script, no inline style, no `eval`**: a test fails on any of them in `web/`. This policy belongs to the admin site: the web player is the app built for the browser and its own policy (WebAssembly and the rest) is decided with its drawings (P6-01); only the token and the signed addresses carry over. Every string written into a page by script goes in as text (`textContent`), never as markup: a person's name is data, not HTML (the join page's rule, `join_page.py`).

**Where it answers.** Under `/encore/`, the namespace the gateway reserves for Encore (`gateway.py`: every other path goes on to the music server, whose own root page and web app must keep working): the pages are `/encore/admin` and `/encore/setup`, their files `/encore/web/*`, their API `/encore/api/v1/admin/*` and `/encore/api/v1/setup/*`. Two short addresses are explicit redirects, so that what a Host is told to type works: `GET /setup` and `GET /admin` answer `302` to the pages above (the query, which carries the setup code, kept) and nothing else is taken from the music server; the route-table test lists them. All of it is registered **before the music server's catch-all** and answers **404, not 403**, to a public request (`api.is_public_request`: the away address or a non-private address), so the internet learns nothing about it (`15` §4: "home network only; never on the public address"). The Host who wants the pages while away uses the tailnet address (Tailscale's own addresses are not public). The app's Host notices ("needs you") reach the Host's phone by the live channel, which is not an admin route. The setup page removes the code from the address bar as soon as it has read it (`history.replaceState`), and is sent with `Referrer-Policy: no-referrer`.

**The first run is a takeover risk, so it is closed by construction (hidden risk H36).**
1. While no owner exists, the server holds a **setup code** (`7KQ-4MZ`: six characters of the 31 that cannot be mistaken for each other, about 30 bits, enough because a wrong try costs a wait and the pages answer only on the home network). It is made by the installer (or `encore firstboot`) and written into `.env` as `ENCORE_SETUP_CODE` (the file the administrator's password is already in: root-only, mode 600), shown once by the installer, on the appliance's console and by `encore status` while setup is pending. The server compares it in constant time and never stores it in the database (it is not a Host choice, so not in `host_setting`, and not server state, so not in `setting`). `GET /encore/setup` without the code shows the sentence of `15` ("Use the link shown on the computer where you installed Encore"); with the right code the page keeps it in memory and sends it as `X-Setup-Code` with every `/setup/*` call. Wrong codes are counted per address (5 a minute) and in all (30 a minute), then a wait that says how long: the address is the one the rest of the server trusts (`client_address`: the connection's own, a forwarded one only from a proxy of ours), never a header a client wrote.
2. The `/setup/*` routes **exist only while no owner exists** (the check is inside each, on every call, not at start): once the owner's account is made they answer 404 for ever, so no URL of the wizard can take over or reset a finished server. **The owner is made under one lock whose last part is one write transaction** (`BEGIN IMMEDIATE`) that checks again that nobody exists and makes the owner in the same breath: two browsers that post at once make one owner, and a person made by another process in between is caught there. A code that is configured but not well formed, or no code at all (the headless door), means the routes do not exist. When the owner is made, the server leaves a marker (`data/setup-complete`; it cannot write `.env`) and **the next run of the `encore` command (any command, and the nightly backup is one) removes the line from `.env`**; the server ignores the code from the moment anybody exists, so a line that lingers is harmless, and `encore status` shows the setup link only while the marker is absent.
3. **Both doors make the owner in the browser.** `install.sh` stops asking for the owner's name and password and prints the setup link, as the appliance does (`--owner NAME` with `--owner-password-file` stays for headless installs and test rigs: it makes the owner as today, and the wizard is then closed from the start). The pages after the owner's account (the music folder, the line test, the add-ons, away from home, the first invitation) are served **signed in** at `/encore/admin/setup/<step>` and appear on the admin Home as "Finish setting up" until the Host has done or skipped each: so a Host who arrives by the headless door, or closes the browser half way, gets the same pages. The progress is `host_setting` `setup_step`. This changes `install.sh`, `install-test.md` and the walked proofs `c01`, `c03`, `c06` (P3-07 walks both doors again).
4. The code is single-use: finishing the owner step deletes it. The owner's password is chosen by the Host in the wizard; **a recovery key** is made at the same moment (§6), **by P3-16, which builds the key and `encore reset-owner` together**: a page must never promise a recovery that no command can do yet, so until then the wizard says nothing of it and an owner made without a key is recovered by root on the computer, as §6 already says.

**Facts the server cannot see, and how Home gets them (slice 4).** The Encore container mounts only `/data` and `/music`. It can measure for itself: the free space of both folders, the music server's answer, YouTube's state, the version it runs, people, devices and today's counts. It cannot see when the last backup was made and where it lies, whether a newer version exists, or when the away address's key expires. **Decision: the `encore` command writes `/opt/encore/data/host-status.json` (inside the folder the server already mounts, read-only for the server)** whenever it does something that changes those facts (`backup`, `restore`, `funnel on|off`, `update`, `secure`, and the nightly backup timer) with `{writtenAt, lastBackup: {at, bytes, locked}, away: {address, keyExpiresAt}, update: {available, checkedAt}, backupKey: {madeAt}}`. Home says in words that this computer has not told Encore yet when there is no file or it cannot be read; a file that has gone quiet (over 36 hours) is still used, because the time of a backup and the end of a key are absolute and an old file can only make a warning come early, never late, and the row says how old the report is. It never shows an invented "all good". The key's end is read from the node's own entry in `tailscale status --json` on the computer (the Tailscale that gives the away address runs on the host), never from a peer's. It needs no helper and gives the server no power; it holds no secret and no path outside the install; the helper's `status` action later answers live in its place.

## 3. The helper (P3-25): a fixed list of actions, never the computer

**The problem.** The page's server must not be able to start, stop or replace containers (P3-04: that power was removed on purpose). Update, back up, restore and "turn on the away address" change containers and the computer. Something else must do them, and it must do **only** a short, fixed list.

**Where it runs: on the computer itself, as a small program that only calls the `encore` command's own subcommands.** The reasons are in what the actions touch. `encore funnel on` installs and drives **the computer's own Tailscale** (`tailscale up`, `tailscale funnel`, ADR-R25), `encore autobackup` writes a systemd timer, and `install.sh` installs Docker and refuses a computer that is not Debian or Ubuntu with systemd: the host contract already is "a Debian-family Linux with systemd and Docker". A helper in a container could do none of the first two without a second way out of the container, which would remove the point of putting it there. So the Docker socket stays in **no** container (P3-04 and P3-25's acceptance stay literally true), and the helper is:
* a systemd **socket** unit, `encore-helper.socket` (`ListenStream=/run/encore/helper.sock`, owned by root, group-readable by the group the Encore server container is added to), with `Accept=yes`, and a template service `encore-helper@.service` that runs `encore helper-session` for each connection as root, then exits. No daemon sits in memory; nothing listens on the network. The socket file is bind-mounted read-write into the Encore server container, and into nothing else.
* `encore helper-session` is a few dozen lines of the existing shell script: it reads **one request line** (`TOKEN ACTION [ID]`), compares the token with the per-install **helper token** in `.env` (the second lock after the socket's file permission), matches the action against a `case` list of exact words, validates the id (`^[A-Za-z0-9_-]{1,64}$`, and it must exist in the helper's own listing), runs the one fixed subcommand with no shell and no string joining, and writes back lines `progress: ...`, then `done: ...` or `failed: ...` (a sentence). The command a Host types and the request the server sends reach the same subcommands, so the two doors cannot disagree and the helper has no code of its own to be wrong in.
* A host without systemd is not a supported host today (the installer says so); if one ever is, the same `helper-session` is reached by the other local-socket mechanism of that host. The list, the protocol and the tests do not change.

**The list, fixed in code**: `status`, `backup.make`, `backup.list`, `backup.verify {id}`, `restore.apply {id}`, `update.check`, `update.apply`, `update.rollback`, `away.status`, `away.on`, `away.off`, `addon.enable {id}` and `addon.disable {id}` (only the add-ons whose manifest names a compose `profile`), `restart`. Anything else is refused and logged, and the refusal is a test.

**What keeps the list small in practice**
* **Arguments are never commands, and the server cannot name an image.** `update.apply` takes no version: the helper reads the release channel (P3-27) itself, on the computer, and applies what it finds, to tags pinned there. `restore.apply` takes only the id of an archive the helper itself made and verified, from its own backups folder.
* **Every request writes one audit line and a job file** (`/opt/encore/jobs/<id>.json`); `encore status` shows the last ten.
* **The updater runs from the OLD image.** An update that recreates the Encore server must not depend on the code being replaced: `update.apply` starts a detached one-shot job (a systemd transient unit) that does the backup, the pull, the restart and the health wait, rolls back by itself if the new version does not answer in three minutes, and writes the job file. A faulty new release cannot break its own undo. A test kills the helper session mid-update.
* **Residual risk, said plainly:** a fully compromised Encore server can ask the helper to update, back up, restore the newest backup, restart and switch a listed add-on. It cannot run a command, read the music, pull an image of its choice, reach another container's files or open a port.

**What stays open for the build of P3-25, with its test:** the group id the container must be given to open the socket (a file mode that is not world-readable, on a stock Debian, Ubuntu and the appliance); that a restore replaces the databases while the server is stopped and the helper session is not inside a container that stops; the exact words of every `failed:` line.

## 4. The admin API

The routes of `17` §3 group "admin" and "setup" are the contract (all *planned*, owner-only, refused from a public request as 404). `GET admin/session` is the first of them: who the page is signed in as (owner only) and, for a browser, when it signs out. They return **counts, states and sentences, never a title, a name of a song, a password, a key or a path outside the installation** (`15` §4, `21`). Errors use the one error shape (`17` §2); an operation that needs the helper and cannot reach it says "Encore's helper is not answering: run `encore status` on the computer" (a sentence, `server_busy`). The route-table test (`tests/test_route_table.py`) forces the table in `17` and the code to change together.

## 5. The button installer (P3-21), and what P3-23 builds

**The rule.** A person who will not use a terminal reaches the setup pages without one, and the installation they get is **the same installation** the command makes.

**First target: the owner's homelab (a Proxmox host that already runs a music server and other tools).** The answer is a **ready-made server image** (the appliance):
* Built in CI by running the real `install.sh --yes --bake` inside a clean Ubuntu Server cloud image under QEMU (the Docker engine installed, the three images pulled, the compose file in `/opt/encore`, the `encore` command and the helper in place, automatic security updates on, **no secrets, no `.env`, no identity key, no `/etc/machine-id`, no SSH host keys, no network lease, no cloud-init instance state**: a cloned image that shared a machine id would share DHCP leases and trip over itself). Published as a release file next to the app (`encore-server-<version>-amd64.qcow2` and `.ova`, with a checksum the page shows).
* **Secrets are made on first boot, never baked** (every appliance has its own administrator login, helper token, setup code, song-signing secret, SSH host keys, machine id and, at first server start, its own identity key: a downloaded image shared by thousands of servers must not share one secret). `encore firstboot` makes them, starts Encore, and prints on the VM's console the line of `15` §1: the address (`http://encore.local/setup?code=...`, and the numeric one as the fallback) and the setup code. **The console of the VM is the proof of ownership**: only the person who controls the hypervisor can see it.
* **What the person does, with the hypervisor's own buttons:** download the image; upload it in Proxmox's web page; create the VM from it (memory 4 GB, 2 cores, a disk, the network bridge of the house); start it; open the link on the console. *To verify on the owner's Proxmox version (P3-07), not assumed*: that the web page accepts the file (Proxmox VE 8.x and 9 have an "import" content type for disk images and OVA files), what its dialogue calls each step, and the cheapest picture for each wall. If the owner's version cannot import without a shell, the fallback is the community-style "paste one line in the Proxmox shell" (the shell is a button in the web page): a terminal in all but name, **said honestly in the guide** and recorded as the wall it is.
* **Walls and their answers** (each a button or a picture in the guide, or the design picks another way): the bridge/VLAN choice (a picture of the three common cases); the VM has no music: the wizard's page 3 offers an empty library, **a second virtual disk**, **a network share (NFS/SMB) mounted by the wizard**, or *Yours* (the owner's existing music server by address and account: `35`, P3-11), and says which each reads or writes; the VM's address changes on every boot (it is found by name, `encore.local`, and the setup link carries the number as well); the clock (a VM with the wrong clock fails certificate checks: the first-boot step syncs it and the Home page warns); disk growth (one sentence and one picture).
* **Same installation, proved by a test, not by hope**: a CI job installs once by the command on a clean machine and once by the appliance, and compares the two installations: the tree of `/opt/encore` (names, modes), the compose file byte for byte, the **names** (never values) of the keys in `.env`, the migrations applied, the answer of `GET info`, and `encore status`. A difference fails the job. P3-07 then walks the appliance and the command once each on a clean machine.

**Second target: a Windows 11 PC (research first, nothing decided).** What it needs today: virtualisation switched on in the firmware, WSL2 or Hyper-V, a Linux with the Docker engine inside; the licence of Docker Desktop for this use (free for personal use and small business, to be checked on the day), and the alternatives (Podman, a WSL distribution that carries the Docker engine without Docker Desktop). The likely shape: a signed Windows installer that checks each wall in words, imports **the same appliance** as a WSL distribution, opens the firewall for the house network only, and shows the setup link. The design for it is written when the first target has been walked.

**Everyone else (a NAS, a Raspberry Pi, a Linux box):** the command door and the website guide; the Raspberry Pi image is P3-17.

## 6. A forgotten owner password (P3-16)

A button inside the admin pages cannot help a person who cannot sign in. The proof of ownership is **being at the computer**: (1) at the end of the wizard a **recovery key** (five groups of four letters and digits) is shown once and offered as a printable page, stored only as a hash; (2) `encore reset-owner` (command door) asks for the key, or, if it is lost, lets a person who is root on the computer make a new password and says that this is what it did; (3) on the appliance, the same is an item in the console's own menu (the button door: the console is reachable only from the hypervisor). Every reset writes an audit line and a notification to the owner's devices that are still signed in ("the owner's password was reset from the server computer").

## 7. What the other items build, exactly

* **P3-25 (the helper)**: §3's list, protocol, tests (every listed action refused with a bad argument; an unlisted action refused and logged; the updater survives the helper being killed; the command works with the web server down), the updater from the old image, the audit and job files. Acceptance as written.
* **P3-23 (the button installer)**: §5's appliance build (`--bake`, `encore firstboot`, the CI job that builds the image and boots it in QEMU headless and checks `GET info` and the setup page), the same-installation job, the guide's pages for the first target. Nothing for Windows until its design exists.
* **P3-06 (the pages)**: §2's slices 1–7, each with its routes, its tests, the page and the screen checklist (`07` §10) at 360 px and on a desktop browser.
* **P3-22 (drawn changes)**: `35` §5, plus: the installer's own console screens (text, `15` §1), the Updates page (the Update button, its way back and its result sentences), Backups (Back up now, the encrypted-archive passphrase of P3-30, Restore with the typed name), Away from home (the page runs the steps), the owner's recovery key page, the appliance console menu (text), Storage (P3-13).

## 8. What the roadmap's coming features need from the server

A coming feature may not be built on something the server lacks. This is the list of what each needs; which of these `main` already has, and the items that close the gaps, are on the board (P3-06's notes).

| Coming feature | What the server must have first |
|----------------|--------------------------------|
| Admin pages, the wizard (P3-06) | Static serving; a browser session; a Host settings store; a health route; jobs (§2) |
| The web player (P6-02) | The same origin as the API; the session model of §2; the same CSP; no CORS |
| An update button with its way back (P3-14, P3-25) | **A refusal to start on a database newer than the code**, and a rollback that restores the pre-update copy (P3-29 part 2) |
| A release channel (P3-27) | Images by pinned tag; a channel file the helper reads (the compose file must not default to a moving tag) |
| Pairing by QR, the app finds the server (P2-19, P2-20) | The server's identity key (signed in `GET info`); a pairing route |
| Jam (P4-02) | The live channel; a room model |
| Lyrics on the server (P2-14) | A table, a route, one outside source asked once for everybody |
| Recommendations, federation, the lossless stack (P4) | A place for a new module: routes in `routes/<area>.py`, a service, a migration and an add-on manifest (`35` §3) |
