# Audit of what is already built — does it fit the vision, and where was a fix shoved in? (5 Nov 2026)

The owner (5 Nov 2026): *"forget future things to be built and focus on what's already built, does it align with our vision, is there something wrong, something we need to change, a fix that we kind of just shoved in there to fix an issue now but will cause us issues later on."*

Method: the shipped code was read, not the plans: `server/encore_server`, `app/lib` (**sampled, not covered**: the app is the larger code base and gets its own pass), the installer and compose file, the CI files, the board's own proof for every item marked built or walked, and the git history. Where a claim could be tested it was tested (B-10 and B-18 were measured). The earlier audit is **`ENCORE-PROJECT-BOOK-2026-11-03.md`** (findings A-1 to A-18, inconsistencies I-1 to I-4; outside the repository, in the workspace's `archive/` folder) with `history/reviews-2026-10-31.md#audit` and `QA-*`; every row below says whether it was already recorded there. The standing rule applies to every row: the fix is the proper one, and a stop-gap carries a removal trigger. **Nothing here is scheduled yet**: the owner and the advisor decide what enters the plan. **This audit records issues; it does not correct code** (owner, 5 Nov 2026). One fix was drafted and measured before that instruction and is held, unmerged, on the branch `held/server-db-lock` (B-10, B-18, B-19); no pull request exists for it.

## What was checked and is fine (so nobody re-checks it)

* **No part of the shipped server holds control of the host computer.** `grep -r docker.sock server/encore_server/deploy` is empty (P3-04's acceptance is true); no browser container.
* **Logins do not reach a log or a report.** The server's access log is off (`__main__.py`, `access_log=False`), the music-server client logs are quiet (`tests/test_logging.py`), and the app scrubs `t`, `s`, `p`, `token`, `Authorization` and JWTs from everything it logs, errors included (`core/logger.dart` `scrubSecrets`, applied to the whole formatted message), so Diagnostics > Copy report is clean. The signed `?sig=` addresses are not scrubbed but expire (6 hours / 7 days).
* **The server writes only inside its own folder.** The picture finder adds `cover.jpg` only under `Encore/` (`cover_finder.py` `_folder_picture` refuses any path that does not start with `Encore/`); the keeper writes only under `Encore/` and refuses anything else (`inside`).
* **The phone's database only ever grows** (`app_database.dart`, schema 7, additive migrations, "never destroy user data"). The server takes a copy of its database before any migration and restores it if one fails (`db.py`).
* **The player does not wedge when a load takes too long** (`playback_engine.dart` ~1124, "giving up for now"): it stops the load, keeps the position, and waits for the connection to come back. One wrinkle: the message always says "Check your connection", even when the slow part is the server.
* **The code carries almost no `TODO` or `FIXME`** (none in the server; the app's matches are variable names such as `todo` and `suffixMeta`); two tests are skipped on purpose (`ENCORE_LIVE`, `IT_NAVIDROME_URL`). The stop-gaps below are therefore not marked in the code: they are in decisions and in what the code does.
* **The library scan holds the database write lock only 35 to 90 ms per 500 songs** (measured: 2,000 songs 0.3 s, 10,000 songs 1.2 s in all), so it does not stall the phones.

**How bad is B-10 / B-18 / B-19 at 1 to 20 people, measured (5 Nov 2026).** The test makes 20 phones do what real ones do in a loop (open the app, ask for 30 picture addresses and a song, report a playback position) against a real server on a real socket. **Today's code:** about 320 calls a second, median 5 ms, but the 95th percentile of the library feed is **2.5 s**, of a picture address 93 ms with a worst case of **11.6 s**, of the library feed worst **12.3 s**: SQLite does not queue waiting callers fairly, so some starve for seconds while the average looks fine. **With the drafted fix:** the same ~320 calls a second (the limit of one Python process), 95th percentile at most 135 ms, worst case 175 ms. Real phones make a call a second at most while they are being used, so 20 people is about a tenth of the test's rate and one server carries a few hundred people who are using the app at the same moment, **provided no request waits for the write lock**. What the test does not measure: audio streaming (CPU for transcoding, the Host's upload), YouTube look-ups, a big import in parallel (`22` section 6). Not yet checked: the web server runs sync routes in a pool of 40 threads (the library default); a slow music server or YouTube answer holds one for its whole wait, so 20 people starting songs at once is near that limit.
