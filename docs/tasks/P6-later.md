# P6 — Later (after the first public version; each needs a decision first)

Jam, friend activity, recommendations, the quality tier and Year in Music are **not** here: the owner put them in the first version
(phase P4, `P4-full-feature-set.md`).

| Item | What must be true first | Notes |
|------|-------------------------|-------|
| **Web/desktop client** | Server API stable (P2/P3); device tokens; **the phone's direct calls to outside services moved to the server (ADR-R38: P2-12 catalogue and previews, P2-14 lyrics, the new-release check, covers); signed addresses for previews and covers** | Flutter web/desktop over the same API; the gateway already serves streams (signed addresses, Range); resume-anywhere and single-device playback already work across clients. A browser cannot call Deezer or LRCLIB itself and cannot run YouTube extraction: it never will, the server does. Unchecked: whether Flutter web can load outside cover pictures, and web versions of the phone-only parts (files, local database, secure storage, background work) |
| **iOS** | Owner decision; Apple developer account; the API schema checked in CI (ADR-R41 T5) so the client is built against it, not against the Android app's habits | Sideloading is not possible for most iPhone users; needs the App Store or TestFlight. Background audio, the lock screen and Bluetooth are platform code behind `audio_backend.dart` |
| **Casting (Chromecast, TV speakers)** | Owner decision | Encore devices are in v1 (P4-07); casting to non-Encore speakers is later |
| **On-device extraction fallback** | Experiment X-3 | Only if server-side resolution gets blocked for many Hosts |
| **TV client (Android TV, Google TV, Fire TV)** | The web/desktop prerequisites above; the ten-foot layouts drawn in `docs/design` (ADR-R42); sign-in by a code entered on a signed-in phone (Quick Connect, ADR-R40 slice D) | Same Flutter code, a D-pad and a visible focus on every control, large type, no hover, no long press, back always works. Apple TV is not a Flutter target: a separate small client or casting (AirPlay) |
| **More languages** (owner, 2026-10-24: **after he has tested and used the app daily; he will ask**) | Every string reachable from one place, no text in pictures (ADR-R42 point 7, prepared in P1-12); the screens' layouts already tested at text scale 2.0 and right-to-left (ADR-R41 T6/T8) | French and Arabic first (right-to-left, Arabic plurals), then Spanish and others he names. Needs: Flutter's ARB files with ICU plurals, dates and numbers by locale, **the server's messages as codes plus parameters (the client words them) so one server serves phones in several languages**, a language picker that starts from the phone's setting, and a person who reads each translation. Catalogue names (artists, titles) are never translated |
| **More accessibility options** (owner, 2026-10-24: **after he has tested and used the app daily; he will ask**) | P1-12 done (TalkBack can sign in, search and play; targets 48 dp; contrast); the design's state gallery exists | Beyond the baseline: text above 200 %, a high-contrast theme, a reduce-motion setting that overrides the system's, a dyslexia-friendly font choice, larger touch targets as an option, captions for lyrics and spoken state changes ("buffering", "server not reachable"), Switch Access and keyboard/D-pad paths on every screen (shared with the TV client), haptic cues, and a round of testing with people who use these tools every day |
| **"Encore OS" image** | Evidence that Hosts struggle to install Linux | Flash-and-boot like Home Assistant OS; large maintenance cost |
| **Audiobooks / podcasts** | Owner decision | — |
