# The phone-app walk by a testing agent, 2026-10-30/31: findings and triage

The owner asked for an agent that only tests, clicks every button and writes down what is wrong, and said he had not yet seen the app being driven. A testing agent walked the app on an emulator (build 122 `ba47e27`, signed in as the dev test person) for about three hours and 112 steps: Home, Search, Library, playlists, albums, artists, Now playing, the queue, lyrics, the notification and media keys, every Settings page, Diagnostics, settings search, rotation, 200 % text, Light and true black, airplane mode, the Back button and double taps. **No crash** (the crash log and `flutter:E` were empty after every step) and the Diagnostics log has no warning or error line.

**Everything seen is the dev VM 106, the old stack running beside the new, on an emulator: nothing here counts as a pass**, and some findings (the album order, Year in Music empty, "Can't reach your server") may be the old stack's data and not the app. It never typed a password, signed in or out, or tapped a catalogue song (every such tap makes the server search YouTube from the owner's home address). It restored what it changed and checked (Diagnostics reads the start state again); one stray: it pressed Back once too often at the Home root, left the app, and dismissed a camera permission prompt of the emulator's Google app (cannot be undone; the emulator's, not the owner's).

**Where to look:** the page with the clips and the pictures is a private artifact of the owner (`(a private claude.ai artifact, not public)`); the agent's full report (41 findings, the steps for each and the screenshot file names, 157 pictures, 4 clips) is `scratchpad\qa-ui\REPORT.md` of the session that made it.

## Triage by D-29 (and D-41)

**Candidates for RC1, to the advisor before any code:**

| ID | What a person sees | Why it enters | Notes found by reading the code |

| Q1 | The download arrow on an empty playlist shows "Downloading…", stays at 0 % for ever, and the playlist is listed in Downloads | misleading control, a download that never ends | Nothing to download should be refused in words or the arrow disabled |
| Q2 | Play and Shuffle on an empty playlist look active and do nothing | a dead control | Disable them, with the empty state's "Find songs" as the one action |
| Q3 | An album and its Play button go A to Z (Play starts with "Any Colour You Like", not "Speak to Me") | a wrong order in the core loop | **The app is right** (`watchAlbumTracks` orders by disc, track number, then title). **The data is the cause**: songs that came in through an import carry no track number, so they fall back to the title. Imported playlists are a common first step, so this is not only the old stack. Fix at the source: the server fills `trackNo` from the catalogue match when it makes the ref, and the app prefers the music server's file track number when the ref has none. **Read on the dev VM 2026-10-31 (read-only):** 41 of the 68 refs have no track number, in 23 albums; **every one has a cover** (so the cover finder, which only looks for refs without one, never visits them), **none has a catalogue id**, and 24 are already kept as files (so their files carry no number in the tag or the name either). The catalogue's search answer has **no track position**; only the album's track list does (checked once: `album/{id}/tracks` gives `track_position` and `disk_number`). So the fix is **not free**: a pass of its own, about two catalogue calls per album (one search to find the album, one track list), paced like the cover finder, written only when the album title and the song title match exactly (a deluxe or remastered edition numbers differently), counted against B14's budget; files already kept are not renamed in RC1 |

## How it is worked

Each RC1 row starts as a failing test (a widget test that reproduces what the agent saw), then the fix, then mutation-checked; all local until the GitHub Actions minutes reset (a push costs about 30 minutes). Items that need the release-candidate pair are written into `b11`.
