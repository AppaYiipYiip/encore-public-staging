# P2 — Songs as references (the new library)

Goal: like, add to a playlist, import, queue and resume **any** song, owned or not; imports in seconds; one device at a time.
Read `../04` §2, §3, §8, §10 and ADR-R4, R5, R8, R9, R11, R14 first. Owner decisions D-2 (one copy per song, personal libraries)
and D-3 (keep on save, download, or plays on 2 different days) are decided.

## The API both lanes build against (v1 sketch; P2-01 turns it into an OpenAPI file in `server/api/openapi.yaml`)

Auth in P2: the existing Subsonic token (`u`,`t`,`s`) validated with Navidrome and cached 10 min; P3-03 replaces it with device tokens.

*Marked 6 Nov 2026 (register B-68): this block is the first sketch, not the contract. `../17` is the contract and the built routes differ in places: the prefix is `/encore/api/v1`; entries are added as `{songs: [{ref, id}], after}`; a play is `{id, ref, at, msPlayed, context}` (the device comes from the sign-in, and the phone makes the play's id); a claim answers the state and no lease; the audio is `GET /encore/stream/{ref}?p=&e=&sig=` with the address from `GET /refs/{id}/stream-url`; there is no multipart import. Keep the block as history.*

```
GET    /encore/api/info                                  → {version, name, features, youtube: ok|busy|paused-until|unreachable}
POST   /encore/api/refs/resolve        [{title, artists[], album?, durationMs?, isrc?, deezerId?, videoId?, coverUrl?}] → [{ref, …}]
GET    /encore/api/library/changes?since=<cursor>        → {refs[], likes[], playlists[], entries[], savedAlbums[], removed[], cursor}
PUT    /encore/api/likes/{ref}         DELETE /encore/api/likes/{ref}
POST   /encore/api/playlists {name}    PATCH /encore/api/playlists/{id} {name?, cover?}    DELETE /encore/api/playlists/{id}
POST   /encore/api/playlists/{id}/entries {refs[], at?}  DELETE …/entries {entryIds[]}   PUT …/order {entryIds[]}
POST   /encore/api/plays {ref, at, msPlayed, deviceId}
GET    /encore/api/playback            PUT /encore/api/playback {ref, positionMs, queue[], index, context, shuffle, repeat, playing, deviceId, rev}
POST   /encore/api/playback/claim {deviceId}   → {leaseId}   (P2-09)
POST   /encore/api/imports {url} | multipart file  → {importId, playlistId, count, unmatched}
GET    /encore/api/imports/{id}        POST /encore/api/imports/{id}/stop
GET    /encore/stream/{ref}            → audio (P1-02 stream, now addressed by ref)
WS     /encore/live                    → events: library.changed{cursor}, playback.changed, device.takeover, import.progress
```
Every write is idempotent (client-generated ids for playlists/entries) so the app's outbox can retry safely.

## P2-01 — Encore server skeleton, song refs and the library API (server) — Size L
* **Order.** Needs: none.
* **Why.** C3, C11, ADR-R3/R4. This is the first piece of the single server (P3 moves the rest in).
* **Context.** Old services are stdlib-only Python (`server/encore-*`), each with its own Navidrome client and token check. The YouTube
  package from P1-01 is reusable as is.
* **Do.** `server/encore_server/` (Python 3.12, FastAPI/Starlette on uvicorn, SQLite WAL via a small repository layer, Alembic or
  hand-written migrations, ruff + mypy strict), modules `accounts` (token check only, for now), `catalogue` (ref creation and
  matching: ISRC, video id, normalised artist+title+duration ±3 s, reusing `textnorm.py`), `library`, `playback`, `live`
  (websocket), `imports` (P2-04), `sources/youtube` (P1 package), `keeper` (keep jobs into `/music/Encore/Artist/Album/NN - Title.opus`,
  tags with ISRC/MBID when known, Navidrome scan, attach `file_id`), the work scheduler of `../04` §10 (in SQLite). Docker image;
  run it **next to** the old services on the dev VM, on its own port, behind `/encore` in the Funnel `serve.json` and at home.
  Scanner link: songs already in the Host's library get refs on first sync (match by MBID/ISRC tags, else artist+title+duration).
* **Acceptance.** Contract tests from `openapi.yaml`; integration test with real Navidrome in Docker: like a catalogue song → keep
  job → file appears → ref gets `file_id` → like unchanged; **rename/re-tag/replace the file → like and playlist entry unchanged**;
  the scheduler tests of P1-03 still pass inside the new server; restart mid-import resumes (J-12).

## P2-02 — The app's data layer on song refs (app) — Size L
* **Order.** Needs: none.
* **Why.** C3. Today local tables are keyed by Navidrome ids (`lib/data/db/tables.dart`: `Tracks`, `Playlists`, `PlaylistEntries`,
  `Pins`, `PlayHistory`…) and synced from Subsonic (`lib/data/sync/sync_engine.dart`, `outbox.dart`, `playlist_mutations.dart`).
* **Do.** Add a `SongRefs` table (ref id, metadata, optional `fileId`), point likes, playlist entries, pins (downloads), history and
  the queue at refs; keep the Navidrome-file index for streaming kept files. The library sync reads `/library/changes` (cursor) and
  listens to `library.changed` on `/encore/live`; the outbox sends the new endpoints. **Migration on first launch after the update:**
  the phone uploads its current likes and playlists (it has them locally) through `refs/resolve` + the library endpoints,
  idempotently; then switches source. One-way mirror back to Navidrome is P3-03's job.
* **Don't.** Drop the local database (people would lose downloads); rewrite screens (they read the same repositories).
* **Acceptance.** Upgrade test on a copy of a real phone database (tester on CT 104): every like and playlist entry present after
  migration, counts identical; a like made on device A appears on device B ≤ 2 s (N9).

## P2-03 — Play is not save; albums and playlists play through catalogue songs (app + server) — Size M
* **Order.** Needs: none.
* **Why.** A3, E4, ADR-R5. Today a tap adds the song to the library (ADR-066) and Play on "Lateralus" (2 of 13 owned) plays 2 songs.
* **Do.** Playing a catalogue song never creates a like/library entry; "Recently played" records it (history). The queue builder takes
  every song of an album/playlist as refs and plays each by its playability (P1-09): kept file, else stream, with the next 2 prepared
  (P1-04). Saving (like / add to playlist / save album / import), downloading, or playing the same song on **2 different days** (server
  setting `keep_after_play_days`, default 2) triggers a keep job (D-3). A song is kept once for everybody.
* **Acceptance.** J-03; the Library does not change after playing 10 catalogue songs; liking one shows it in Liked Songs at once and
  the server keeps it in the background; a song played yesterday and today is kept (test with a controllable clock); two people
  keeping the same song produce one file.

## P2-04 — Imports in seconds (server + app) — Size M
* **Order.** Needs: none.
* **Why.** B5, B6, E9; owner: "in Spotify it's 5 seconds".
* **Context.** Measured list reads: YTM 189 songs in 2.1–3.2 s (`ytmusicapi.get_playlist`, all with video ids); Spotify embed ≤ 100
  songs in 2.2–3.5 s (`__NEXT_DATA__` → `props.pageProps.state.data.entity.trackList`); file imports exist in the app
  (`lib/domain/import_file.dart`: Spotify data zip, Exportify CSV, YouTube Music CSV).
* **Do.** `POST /imports`: read the list, create refs in bulk (video ids attached when known), create the playlist (cover = source
  thumbnail), return; queue matching (Spotify-sourced, priority P2, visible rows first) and keeping (P3 priority; if D-3 keeps
  imports). The app shows the playlist from the response at once; counts come only from the server's import record (one source).
  Unmatched entries show "Not found" with a "Find it" search. Share-to-Encore from Spotify/YouTube Music opens the import directly.
* **Acceptance.** J-04 (189 songs in Your Library ≤ 5 s, right count, song 57 audible ≤ 3 s); a 1,000-song Spotify export file:
  playlist visible ≤ 15 s.

### N-26 — Who is the artist of an imported upload (design; audit B-125) — Size M, five slices

*Design only: no code exists. Slices 1 and 2 are the fix; 3, 4 and 5 each wait for the proof or the trigger named in them.*

**What goes wrong.** A YouTube upload is not a song of a catalogue. YouTube Music's own list says who the *uploader* is and calls that the artist. The importer
files the song under it: "Tinariwen - Full Performance (Live on KEXP)" becomes a song of an artist named KEXP, which then has a folder, an artist page and a
picture look-up of its own. More than half of the 100 artists the music server had no picture for (N-15) were channels, labels or accounts, not performers.

**1. The cause, proved** (the real functions called on the real strings; the code of commit 346883b; the JSON around the strings is the shape of a recorded
entry, because no recorded answer of a person's upload exists yet, see slice 1 step 0).

| Reader (production: YouTube Music; fallback: yt-dlp) | Input: video title / uploader channel | Output (artist, song) | Why |
|-|-|-|-|
| `_ytmusic_tracks` (`videoType` UGC, and also with none) | `Tinariwen - Full Performance (Live on KEXP)` / KEXP | **KEXP**, the whole title | `names[0]` of `artists` is taken for every kind of entry; the title is never read |
| same | `Sepultura, live at Hellfest Open Air 2026 – ARTE Concert` (en dash) / ARTE Concert | **ARTE Concert**, the whole title | same |
| same | `DAN DA DAN Opening \| Otonoke by Creepy Nuts` / Crunchyroll | **Crunchyroll**, the whole title | same |
| `_youtube_tracks` → `split_artist_title` | the first / KEXP | **`Full Performance (Live on KEXP)`**, `Tinariwen` (sides swapped) | `_is_channel` is a substring test on letters only: "kexp" is inside "fullperformanceliveonkexp", so the right side "is the channel" and the sides swap |
| same | the second / ARTE Concert | **ARTE Concert**, the whole title | an en dash is not a separator; no separator makes the channel the artist |
| same | the third / Crunchyroll | **Crunchyroll**, the whole title | no " - " in the title makes the channel the artist |

The first three rows are exactly the rows stored on the test server (audit B-125): the stored rows came from the YouTube Music reader, the one a server with
`ytmusicapi` uses. The yt-dlp reader (a server without it, or when it fails) is wrong in its own way. **Two causes, one consequence:** (C1, primary) the
YouTube Music reader trusts the uploader for every kind of entry; (C2, fallback only) the channel test is a substring test, ASCII-only (`_fold` keeps
a-z0-9, so an Arabic, Japanese or Cyrillic name folds to nothing and is silently "no evidence": the same trap as B-37 / P2-25), and only a hyphen with
spaces is a separator. (The recorded video *search* `tests/fixtures/ytm/surah-al-baqarah-mishary-alafasy.videos.json` shows the same shape: a video hit's `artists` is its uploading channel, "Alafasy Recitations".) Entries that are right today and must stay so: in the recorded `tests/fixtures/ytm/playlist_community.json` 146 entries are
`MUSIC_VIDEO_TYPE_ATV`, 1 is `OMV` (Lil Wayne, "Lollipop"), 2 are removed catalogue entries with no `videoType` and an album; `playlist_album.json` has 10
`ATV`. Reproduce: from `server/encore_server` of the live clone, `python -c` (NOT a script path, NOT `-I`) calling `read_playlist(url, ytmusic=lambda i: data)`
and `split_artist_title(title, channel)`. **Trap:** `C:/dev/venv-encore-server` has `encore_server` installed from the OLD archive clone `encore\`; a script
started by path (or with `-I`) imports that copy. Run `python -m pytest` or `python -c` from the live clone's `server/encore_server` and print
`encore_server.__file__` first.

Who else could store a channel as an artist (checked by search): the **file import** (`import_file.dart` → `refs.parse_item`) takes the artist column the
file gives (Spotify exports, Exportify, a YouTube Music takeout "library songs" file: the file's own artist, not an uploader; whether a takeout row of an
upload carries the channel is not known without a real takeout file); **`lean.candidate_from_video`** reads the channel of a *search hit* as the artist, but a
`Candidate` is only scored and never becomes a ref's artist (only `scoring.py` reads `.channel`); the future catalogue search (P2-12, "video" and "song"
hits tapped into refs) **must go through the same door** (below). No other reader exists.

**2. The rule: the channel is the uploader, and the uploader is evidence, not the artist.** One function, `read_upload(title, uploader, *, kind,
declared)`, in its own module next to `readers.py`; both readers call it; so will the file import if a takeout needs it and P2-12. It returns the artist, the
song title and **how the artist was decided** (`basis`).

| What the source says | The artist is | `basis` |
|-|-|-|
| `videoType` ATV, OFFICIAL_SOURCE_MUSIC or OMV; or **no `videoType` on an entry that has an album** (a removed catalogue entry: the recorded ones have one; "unavailable" alone is NOT evidence, see the amendment under "Slice 1, as built") | the artists YouTube Music declares ("- Topic" and "VEVO" stripped) | `declared` |
| a "- Topic" channel (yt-dlp has no `videoType`) | the channel without "- Topic" | `declared` |
| `videoType` UGC, **any value this code does not know** (a missing one on an entry with no album included, available or not), or yt-dlp's flat listing | what the title says, else the uploader (below) | `title` / `channel` |
| a Spotify, file or catalogue description | as given | `declared` |

An unknown `videoType` is an upload on purpose: the safe default never trusts the uploader's name as a performer (values seen in the wild but not yet recorded, such as a person's own uploaded track or a podcast episode, are uploads until step 0 records them). An upload is read in this order (slice 1):

1. **A title with a dash (hyphen, en dash, em dash, with spaces, outside brackets) is `Artist - Song`.** The channel only breaks the tie the other way: when it
   is a *whole name* of an artist the RIGHT side lists ("BELLAKEO (Video Oficial) - Peso Pluma, Anitta" on the channel Peso Pluma) the title is `Song - Artist`.
   "Whole name" = Unicode-folded (NFKC, case-folded, letters and digits of any script), with the channel's own decoration ("Official", "VEVO", "- Topic")
   removed, equal to the side, or to one name of a credit list (`,` `&` `x` `feat.`). **Never a substring.** `basis = title`, **except** when the artist is
   reached only because the whole right side equals the uploader and names nobody else ("Sepultura, live at ... – ARTE Concert"): then `basis = channel`. The
   title agrees with the uploader only by repeating its name, and a broadcaster and a performer look the same here. Kept as `title`: the LEFT side is the
   channel ("Arcangel - FN8" on Arcangel) and a right side that is a credit list naming someone else ("... - Peso Pluma, Anitta"). **Cost, written down:** a
   performer's own "Song - Artist" upload is weak too; slice 2's rule (a name with one `declared` or `title` song is an artist) absorbs it.
2. **No dash: the uploader, `basis = channel`** (a VEVO channel is the artist's own: its name without "VEVO", still `channel`, because "TaylorSwiftVEVO" has
   no space). This is the one stop-gap and it is named below.
3. **Brackets never decide who the artist is.** A bracket that names a venue, a show or a label ("(Live on KEXP)", "(Live at Wembley)", "[A COLORS SHOW]")
   stays in the song title, as `clean_title` keeps it today: it says which recording this is.

Slice 4 adds the *shapes of context* the audit's other two examples need, each behind a negative corpus (section 5): `Artist, live at Venue` and
`<Artist, live at V> – <the channel's own name>` (the right side is a credit, not the artist: ARTE), and `<Show> Opening | <Song> by <Artist>` (anime openings:
the "by" form is read **only** after a series label that ends in "Opening" or "Ending", never alone: "Stand By Me" must stay a song). Prototype run (scratch
file, not part of any PR) over the audit's three strings: slice 1 alone gives Tinariwen right and leaves ARTE Concert and Crunchyroll as today; with slice 4
all three come out right (`Tinariwen` / `Sepultura` / `Creepy Nuts`); over 17 titles that are correct today (`Ed Sheeran - Stand By Me`, `Ed Sheeran - Shape of You | Official Video`, `Chopin - Nocturne Op. 9 No. 2 | Piano`, `Bohemian Rhapsody - Queen` on "Queen Official", `We Live in Fear`, an Arabic `Artist - Song`, ...) it
changes nothing. A first, wider word list (`op`, `ed`, `ost`, "session", any "live in") gave the artist "Me" to `Ed Sheeran - Stand By Me`, the uploader to `Chopin - Nocturne Op. 9 No. 2 | Piano` and the artist "We" to `We Live in Fear`: **that is why the shapes are a later slice with their own corpus.**

**What YouTube cannot tell us (written down, not hidden).** U1: a personal upload account whose title names nobody ("Windowpane (Official Video)" on a
channel that is the band's own or a stranger's: the two look the same; the "official artist channel" badge is not in what `ytmusicapi` or yt-dlp's flat
listing return, to be checked on the real answer in slice 1 step 0). U2: which side is the artist when neither is the channel (`Song - Artist` against
`Artist - Song`; default `Artist - Song`, the dominant order, as today). U3: an upload that is not a song (a full session, a DJ set, a recitation): the song
title is the video title, the artist is whoever is named. U4: a performer named only in the description (a flat listing has none).

**The stop-gap for U1, and its removal trigger.** The channel stays as the visible artist, exactly what YouTube Music shows for that upload, flagged `channel`.
It costs: a name that is not a performer is in the library's artist list until slice 3. The flag exists so that no such name ever gets a picture look-up or an
artist page (sections 3, slice 2 and slice 3). **Removal trigger:** when the catalogue can identify an artist from a song's title (P2-12, the server's
catalogue search, or N-14's catalogue artist per library artist), a background errand upgrades a `channel` song to `declared`. Proposed task: **N-26b**
(not created: the lead decides).

**4. Rows already stored.** Fixing the readers changes only new imports. `refs._enrich` never rewrites a stored artist or title (identity: likes, playlists and
the kept file point at the ref), so importing the same link again finds the old ref by its video id and keeps the old, wrong artist. Facts to keep, so that
this and any later, better rule is a re-derivation and not a guess (slice 2, one migration): `song_ref.artist_basis` (`declared` / `title` / `channel` / null for
a ref made before this or by a client) and `song_ref.uploader` (the channel's name, when the song came from an upload). Set only by the importer through
keyword arguments of `refs.resolve`, **never parsed from a client's JSON** (`parse_item` is shared with phones; a client cannot mark itself "declared"). `_enrich` fills a null basis only when the artist agrees.

*What a repair of a stored wrong row needs (slice 5, sketch; its own note before code).* The row is recognised exactly: its stored artist equals the
uploader (stored, or, for a ref made before slice 2, got by reading the import's playlist again, one YouTube Music call per playlist) **and** the new reading says
otherwise. A true "channel" song reads the same twice and is never touched. Then: (a) update `artists`, `title`, `norm_key`, `artist_basis` of the ref; likes,
playlist entries and plays point at the ref and survive; a changed `norm_key` may now equal another ref's (the index is not unique): two refs for one song is
the B-71 situation (`find` returns the first), not new, and no merge by name is attempted (`refmerge.py` merges only refs that share a file: "never on the
name alone"); (b) the kept file under `Encore/KEXP/...` needs its tags rewritten, its folder changed and a scan: the keeper has no "re-place a kept file" step
today and a moved file is a new song for the music server (its ids follow the path), so the phone learns it through the files feed like any replaced file; (c)
the artist's old folder and its `artist.jpg` are left to the Host. **Recommended default (decided here, yours to overrule): do not build slice 5 now.** The
test server's rows are test data and are reset and re-imported by the lead; no stranger has a library yet (no published image, the join and invite steps
are not walked; nobody else has an install: P2-11 is closed for the same reason). That holds only while slices 1 and 2 are in the **first public image**:
add that to `RELEASE-CANDIDATE.md` as a gate. **Trigger to build slice 5:** any install other than the owner's test server holds an import made before them.

ITALIANO" an artist), or a side that only describes the upload or the version ("Song - Official Video", "Song - Live in Moscow") keeps the credit. **A recorded

YouTube alone, pinned by a test, removal trigger N-28. The rule can still misread `Song - Subtitle` under a band's credit (a side that is neither the credit nor a version
word); N-28 fixes both. (c) A fourth basis, **`unknown`**: nobody is named (the recorded OMV `Akudama` has an empty `artists`; a Spotify track may have none). The reader says

tombstones), only by its ids, so two different nameless songs with one title can never share a ref; `artist_finder` never asks the catalogue about it. Slice 2 (below) stores
the basis `unknown` on the ref and treats it like `channel` in the finders. (d) `Track` carries `artist_basis` and `uploader` in memory only. (e) Step 0 recorded nine YouTube Music *search* answers (`videoType` and `artists` as the
service gave them), not `get_playlist` answers: a test builds a playlist entry from the shape of `playlist_album.json` filled with the recorded values. (f) Names are compared by
their letters in any alphabet (`uploads._name_key`); the server's own `textnorm.ascii_fold` still folds an Arabic or Cyrillic name to nothing (B-37 / P2-25), a test pins

**Slice 2, as built (15 Nov 2026; built, not walked).** Migration `0014_ref_artist_facts.sql` adds `song_ref.artist_basis` and `song_ref.uploader`, nullable, nothing else: no default, no check, no update. **NULL means "as before" (a performer), never `channel`**; the value is checked in `refs`, not by the schema, so a fifth basis costs no table rebuild. The vocabulary lives in `artist_basis.py` (no dependency on `imports` or `refs`). `refs.resolve(..., artist_basis=, uploader=)` takes the facts as keyword arguments: a link import passes them (`ImportService._facts_of`), a file import, a phone's `POST refs/resolve` and the library scan do not (a client's `artistBasis` is ignored, tested at both doors); a basis nobody knows is refused with a `ValueError`. **Decisions.** (1) *Facts are only FILLED, never rewritten* (`refs.facts_to_fill`, the one rule for `_enrich` and the merge repair): the design (section 4) says only "fills a null basis only when the artist agrees" and nothing of an upgrade, so a set basis is never changed by a stronger or a weaker reading; an upgrade (a Topic upload after a personal one) goes with the artist, title and key it describes, which are slice 5's and N-28's. (2) The basis is filled only when the reading names the same artist as the ref (as the name key compares them); `channel` and `unknown` additionally only when the ref plays from the very video the reading came from, because they are facts about THAT upload: a performer's catalogue ref (NULL) found by name for an upload on the band's own channel must not be downgraded, or the finders would never look for its picture. (3) The uploader is the channel of the UPLOAD the ref was made from: a NEW ref stores it whatever the video (the design's definition has no video in it, and the two real removed uploads have none and are exactly the rows that need it; cost: a later search may attach another video, the uploader stays the original's; the alternative, stored only with a video, would have said nothing about them), a ref FOUND takes it only when it plays from the very video the reading came from, and then whatever the artist, because it is what the repair of slice 5 needs to recognise a ref filed under its channel (its stored artist equals its stored uploader). (4) The merge repair (`refmerge`): the new columns are in `_NOT_COPIED` (the generic copy would carry the facts of the loser's artist over to a survivor that keeps its own) and follow the same rule: the basis follows the artist, the uploader follows the video the survivor will hold. (4b) The keeper (kept songs) is the third caller that sends an artist and a title to the catalogue, for a song that has no cover, thumbnail or video thumbnail: it reads the stored basis from the row (the ref a phone sees has none) and asks nothing for `channel`, `unknown` or the placeholder name; the song is kept all the same. (5) The picture rule keys on the stored basis: `artist_finder` asks about a name only with the songs whose basis is not `channel` or `unknown`, so a name whose songs are ALL such is not asked about and nothing is remembered; `cover_finder` leaves `channel` and `unknown` songs out of its pass (the lead's "never"; the cost: a band's own-channel upload loses a catalogue cover until N-28 and keeps its video's thumbnail, P1-26) and does not send the placeholder name (`[Unknown Artist]`, which the library scan gives an untagged file, with no facts) either. The SQL says `(artist_basis IS NULL OR artist_basis NOT IN (...))`: a bare `NOT IN` is NULL for a NULL row and would silently drop every old ref. (6) Not exposed: `row_to_ref` builds the JSON field by field and a test pins that no key of a ref mentions the basis or the uploader; `docs/17` does not change. (7) The janitor's schema guard needed no change (the names `artist_basis` and `uploader` are not pointers). Still open: slice 3 (no artist page for a channel: a proof on the real music server first), slice 4 (the shapes of context), slice 5 (repair of stored rows, trigger-gated), N-28 (the catalogue names the artist of a `channel` song).

* **Slice 2 (app + a little server), designed 2026-10-25: songs and covers by signed address.** Only the `stream`, `download` and `getCoverArt` rows of the table; browse, search and the password come later.
  * **Songs.** In Encore mode the app asks `GET /refs/{id}/stream-url` for **every** song, kept or not (the server picks its own file, then YouTube: `/encore/stream` already does). **2. Two jobs, two layers: the **identity key** (`refs.norm_key`) stays conservative (it keeps "the" and "and", it never guesses); the **comparison** a client types against (search) may be looser, on top of the same fold, and is P2-12's.

**3. The fold table (the contract; every row is a fixture row; run on the prototype).**

Everything that is not a letter, a digit or a kept mark (punctuation, symbols, emoji, `_`, spaces, the Arabic comma `،`, the ideographic comma `、`) is a gap, as it is for ASCII today. `ARTIST_SPLIT` gains the Arabic comma and semicolon `،` `؛` and the ideographic comma `、` and `;` (a joint credit in Arabic or Japanese is cut like "A, B"); the words for "and" in other scripts (`و`, `и`, `と`) are NOT added (a word inside names is not a separator: P2-12b's credits, F13). `_BRACKETS` gains the brackets Japanese and Chinese titles live in: `【】 「」 『』 〔〕 〈〉 《》` (`【MV】夜に駆ける` has a bracket to remove; the full-width ones become ASCII at step 1). **Cross-check of the Arabic and Persian rows against Lucene (D1, ruled 15 Nov 2026).** The `ArabicNormalizationFilter` of Lucene (`org.apache.lucene.analysis.ar.ArabicNormalizer`) turns the alef with madda, with hamza above and with hamza below into plain alef, alef maksura into yeh and teh marbuta into heh, and deletes the tatweel and the eight vowel marks U+064B-0652; its `PersianNormalizationFilter` (`org.apache.lucene.analysis.fa.PersianNormalizer`) turns Farsi yeh and yeh barree into yeh, keheh into kaf, heh with yeh above and heh goal into heh, and deletes the hamza above; its `PersianCharFilter` turns the zero-width non-joiner into a space; neither folds the hamza seats `ؤ ئ ء`. **Result: every row of step 4 agrees with them** (`آ أ إ→ا`, `ى→ي`, `ة→ه`, `ی ے→ي`, `ک→ك`, the tatweel and the harakat gone, the hamza seats kept apart), with three differences. (i) **Two rows were ADDED by this cross-check**: `ۀ` and `ہ` to `ه` (the first draft kept the Urdu heh forms apart; `ۀ` must be mapped BEFORE step 3, because its canonical decomposition leaves the letter `ە`, not `ه`, once the hamza above is removed). (ii) This design also folds alef wasla `ٱ` to alef and removes the marks U+0653-065F, U+0670 and the Quranic marks, which Lucene leaves (a superset: they are decoration, and `ٱلله` is how the name of God is often written). (iii) Lucene folds toward the Persian letters in one filter and toward the Arabic ones in the other, and the two make the same classes; this design picks the Arabic letter of each class, as `docs/19` names them. `ة→ه` is lossy (a few real pairs differ only there) and is accepted, because an identity is never the title alone: the artist and the length are in it too. **Honest limit:** this is written from the documented behaviour of the filters; their sources could not be opened from this session (no network), so slice 1 reads them, records the Lucene version in the fixture header and gives each mapping a row.

**4. `survives_fold_whole`: the one rule every caller uses.** `textnorm.survives_fold_whole(text) -> bool` answers "can this name be compared by key without losing what tells it apart from another name": the text holds at least one letter or digit, and the fold keeps one word character for every letter, digit and kept mark **that the table does not remove on purpose** (the decorating marks, the tatweel and the format characters of section 3; a letter may become two, `ß` is `ss`; none may become none by accident). It guards against a WRONG match (an over-merge, a wrong stamp, a wrong move), not against a miss: `Don’t` survives (no letter is lost) and still gets another key than `Don't` until slice 2, which is a duplicate, never a wrong answer. **Callers:** N-34 slices 1 to 3 (the identity match and the new keeps), N-34's repair `refile`, the cover finder (B-133), every later repair that moves or stamps by name. It is called on every string the caller then compares by key: the lead artist, the title, and the album when the album is compared. **One function, defined once, and described in ONE place of the documents: this part.** It is DEFINED by P2-25 slice 1 (in `textnorm.py`, with the `survives` rows of the shared fixture); **N-34 slice 1 imports it and cannot start before P2-25 slice 1 has merged** (slice 1 moves no server caller, is small and merges alone). **6. What the matcher does once Arabic is not empty.** (a) **Thresholds were calibrated on Latin characters.** `MIN_TITLE_SIMILARITY` is 0.6 and `MIN_ARTIST_SIMILARITY` 0.9, on `difflib.SequenceMatcher` characters. *Run:* `사랑해` against `사랑이` is 0.667, `мой` against `мои` is 0.667, `حبيبي` against `حبيبتي` is 0.909, `夜に駆ける` against `夜を駆ける` is 0.8, while `봄날` against `봄밤` and `初恋` against `初戀` are 0.5. A Korean, Chinese or Japanese syllable or character carries a whole word, so at the same ratio the dense scripts are MORE permissive than Latin: until now they were never accepted at all, from now on a title of three Hangul syllables one letter off would be accepted. **The rule (default):** a title or artist whose folded text is at most four characters and consists only of Han, Kana or Hangul is compared for EQUALITY, not for 0.6; longer ones keep the thresholds until the 40 real searches of N-16 (which holds Japanese and Arabic lines) measure them. (b) **Version words are English.** `VERSION_WORDS` and the noise words are English, so a live, karaoke or remix upload with an Arabic, Russian, Japanese or Korean marker is not penalised; a bracket's words still count in `version_signature` (so `(ライブ)` makes a different recording by itself). The per-language lists are DATA (a table next to the code), added only on the evidence of N-16's set and read by a native speaker (the owner reads Arabic); none is invented here. (c) **Chinese and Japanese word boundaries.** The identity key is the WHOLE folded string; there are no n-grams in a key, and `ratio` is character-level, so no tokenizer is needed. n-grams (one token per Han, Kana or Thai character, a phrase when querying) belong to the phone's search index, which is B-84. (d) `MATCHER_REVISION` goes up by one in slice 2: every song that earned a seven-day `not_found` because an Arabic result was rejected is believed no more (`missing.standing_of`), the matcher revision is what voids older answers at once; **and the janitor sees those verdicts as no longer live**, so refs that were kept alive only by one become retire-able (`ref_janitor` reads the same constants).

**7. The stored keys and the repair (the part that changed most since 6 Nov).**

*What exists now that did not.* `song_ref.norm_key` is stored and indexed (`song_ref_norm`). The merge repair `refmerge.py` runs at every start and merges refs that share a file, leaving a row in `ref_merge`; the janitor retires unpointed refs and leaves `ref_gone`; the phone reads three feeds with their own cursors (files, merges, gone). A repair that touches a ref's identity has to keep all of that true. **What a wrong attachment is, in the data:** not a `ref_merge` row (a tombstone means two refs shared a FILE, which is real evidence) but ONE live ref holding several `song_file` rows of different music-server songs (`find` matched the second Arabic file to the first Arabic ref by the key `||`, `attach_file` obeyed).

**Step 1: the rekey, at start-up, before any thread (`keyrepair.py`, the precedent is `refmerge.repair`).** After the migrations and BEFORE `refmerge.repair` (so the tombstones that run writes carry new keys). Once, when `setting.textnorm_revision` is below `TEXTNORM_REVISION` (the constant lives next to the fold; the first value is 1; the old fold is revision 0): a backup (`db.backup("before-key-rewrite")`, its path logged), then ONE transaction: for every `song_ref`, `norm_key` becomes `norm_key(lead artist, title)`; **a rewrite never merges**: two refs that now share a key stay two (a key is a lookup, merging is by file, ISRC or the N-11/B-110 rules, never by name afterwards); the same transaction fills the worklist (below); the revision is written last. It is idempotent, it rolls back whole, it logs and never stops the server (a failed rewrite is tried at the next start; the cost while it has not run is that a non-Latin song described again may make a duplicate ref, which the by-file merge folds later; a loud log line says so). Every later change of the fold is the same mechanism with a higher constant: **this is the permanent part**, the first thing a fold change used to lack.

**The worklist, and who is suspect.** A ref is *suspect* when its OWN text did not survive the OLD fold: its lead artist or its title fails the era-0 form of `survives_fold_whole` (a property of the text, so it needs no copy of the old function; it is kept frozen in `keyrepair.py` as `_lost_by_old_fold`, because it describes how stored data was made). This covers `||`, `fairuz||`, `fairuz|habibi|`, `Łukasz`, the lot, and it is decided from the ref's title and artists, not from its stored key (the stored key of `fairuz|habibi|` is not empty). A suspect ref that holds at least one `song_file` of source `library` gets a row in a new table `ref_recheck(ref TEXT PRIMARY KEY, at INTEGER NOT NULL, moved INTEGER NOT NULL DEFAULT 0)`; no foreign key (like `file_log.ref` and `ref_gone.ref_id`: a worklist is not a reason to keep a ref, and a row whose ref is gone is dropped by the pass); `tests/test_ref_janitor.py` (which compares its list of pointers with every foreign key and every column named like a ref) and the song-id helper of `tests/test_ref_merge.py` are taught that this column is a worklist and not a pointer. Keepers' files (`source` `youtube` or `quality`) are never re-judged: the keeper attached them on purpose for the ref's own description.

**Other stored data the broken fold made (decided, not left).** (a) *Covers.* `cover_finder` stores the Deezer cover of a hit that matched by name, and `by_album` copies one URL across every Arabic album of a pass (section 1c): those `cover_url`s are stored and are never asked again (the finder only wants `cover_url IS NULL`). In the same transaction as the rekey, **a suspect ref whose `cover_url` is on Deezer's picture host (`dzcdn.net`, `deezer.com`) and whose `deezer_id` is NULL gets `cover_url` and `cover_tried_at` cleared**, and `touch_file` and `touch_ref_holders` tell the phones that hold it; a cover that was right is found again by the same finder with the new fold (one paced look-up per song, the finder's own `per_pass` and pause). A ref with a `deezer_id` (identified by the catalogue) and every Latin ref keep theirs. (b) *Artist pictures (N-15).* `artist_finder` is guarded (`pick_artist_picture` returns nothing when either folded name is empty: *read*, `artist_finder.py:91`), so its failures were misses, never a wrong picture, and a miss is retried after 7 days (`RETRY_AFTER_MS`): nothing to void; a mixed-script title that collides still picks the picture of the right Latin artist. (c) *Misses* in `cover_tried_at` are retried after 7 days by the finder itself. (d) **Not recoverable by the server: the picture already written into a kept file and the `cover.jpg` the finder wrote into an album folder** (`_folder_picture`, which leaves an existing one alone): they are on the Host's disk, the music server shows them, and only a retag or the Host deleting the wrong `cover.jpg` fixes them; the retag machinery of N-34 and N-26 slice 5 takes the corrected cover from the ref, and the design says so for them.

**Tombstones: `ref_merge.norm_key` cannot be rewritten.** The row stores the deleted ref's key but not its title or artist, so the new key cannot be computed. Rule: **a tombstone whose key had an empty segment is set to NULL** (it can never be found again anyway: no new key has an empty segment; its ids keep working through `canonical` and `find`'s id lookups); the other keys are left, stale for the names whose characters the old fold dropped (`bjrk|...`), which no description produces any more: dead weight, never a wrong answer; the cost is that a song merged away before the rewrite and described again with such a letter makes a duplicate that the next by-file merge folds. **And the next revision will not have this problem:** migration adds `ref_merge.title` and `ref_merge.artist` (nullable), filled by `refmerge` from the loser's row from now on; an old row stays NULL. A default, yours to overrule (section 15, D10).

**Step 2: the rehome, in the hourly library link (`rehome.py`, called from `scanner.link_library`).** It cannot be a start-up step: `song_file.meta` holds no title or artist (`_META_KEYS`), so judging a file needs its tags, which the scan reads anyway (`navidrome.songs`), and a start-up that waits for the music server is a start-up that does not start. A pass begins by reading the worklist and the `song_file` rows of those refs (**every** library row, not only the scan's holder, which is the OLDEST row: a second ref's row of the same file would never be seen through it); for each such row whose `navidrome_song_id` is in the pages, it describes the song with `scanner.described` and decides, in this order:
1. `refs.find` on the tags' description (ids first: an ISRC the ref holds means it IS that recording, then the new key, then the tombstones). If `find` returns THIS ref: **keep** (a fresh scan would have put the file here).
2. Otherwise **move**: the target is the ref `find` returned (an existing song) or `refs.resolve` makes (a new one, with the id, the title and the artists the file's tags give); the row `UPDATE song_file SET ref` moves with its id, `added_at`, `meta` and `source` (a delete and re-attach would lose them and open a window in which the feed says `file: null` and a phone could drop a download); if the target already holds a row of the same music-server song (the keeper's), the moved row is dropped and the target's stays; one `preferred` file per ref is restored on both refs (the rule of `refmerge._merge_files`); `refs.touch_file` on both, `library.touch_ref_holders` on both.
3. **Tags whose artist is the placeholder** (`[Unknown Artist]`, the untagged file of the Host's) are judged by IDS only: `refs.find` returns nothing for that name on purpose (`is_unknown_artist`), and "nothing" must never read as "another song": when no id names another ref the file STAYS. (A suspect ref can carry the placeholder artist and an Arabic title, so this case is real; the row "an untagged Arabic file stays on its ref" is in slice 4's tests.)
4. A file whose tags give no usable title and artist is **not judged** and stays (counted in the log).
At the end of a COMPLETE pass the worklist rows it read are deleted (a file not seen was pruned by the same pass). One backup (`before-rehome`) is taken before the first move. **`rehome.py` means re-pointing `song_file` rows and nothing else: the file stays where it is. It must NEVER rename, move, retag or delete a file of the Host's own music library** (a stranger's existing music folder; the product works beside it); only a file the keeper wrote under the server's own `Encore/` folder may ever be moved, and then by the `refile` machinery of N-34, never by the rehome (`rehome.py` imports no module that writes to the music folder, and a test says so). Each move is one INFO line with ids (no titles), and `ref_recheck.moved` counts them for the log. **Only a suspect ref is ever asked**: the rule "a file belongs to the ref that holds it, whatever its tags say" stays the rule everywhere else, because a Host who retags a file has not said "this is another recording".

**Order of the start-up and of the first pass.** migrations; `keyrepair` (keys, worklist, `ref_merge` tombstones); `refmerge.repair`, which now **holds** a pair when either ref is on the worklist (a new reason `recheck_pending`, logged with the others), because a file that two refs hold may be on the wrong one of them and merging identities on its strength would put one song's likes on another (the same sentence refmerge already says for `same_playlist`); then the threads; the library link's first pass (20 s after start, `first_after_s`) does the rehome; from the second start `refmerge` merges as usual whatever two refs still hold one file.

**8. What a split does to the feeds, and the options weighed (evidence from the code).** *Read:* a file moved from ref R to a new ref B is two `file_log` rows (`touch_file(R)`, `touch_file(B)`); `library.files_since` returns **the current state** of every ref with a row after the cursor, and `refs.get_ref` carries the whole description (title, artists, album, ids, cover, `file`): the phone's `upsertRefs` inserts B (`insertAllOnConflictUpdate`) and updates R, and R's `file_id` and `audioKey` (`refAudioKey`: size, suffix, bit rate, duration, sampling) change, so a download of R is **stale by the key it already has** (`download_planner.dart:116-118`) and is fetched again from what R's file is now. So: **no new feed, no tombstone, no `ref_merge` row, no `ref_gone` row**: no id disappears, nothing is told in reverse, and every like, playlist entry, play, queue position, saved release and download of R stays on R, which keeps the first title (what the person saw). A phone that was away for a year reads the same two rows from the same cursor. R, left with no file and nothing else pointing at it, is retired by the janitor after 14 days with a `ref_gone` row like any ref (its files changed, so it lives 14 days). *Not proven:* the phone's reading of such a page; slice 4 writes the app test of it (a page with R's file changed and a new B; a stale download; no row dropped) with a fixture the server's test writes.

Three ways weighed. **(A) Move the files to their own refs (chosen).** Costs one code path and a once-only worklist; leaves nothing on the phone to un-do; never merges or deletes an identity. **(B) Re-create the old ids / run the merges in reverse.** Rejected, with the code that proves it: `ref_merge.old_id` is UNIQUE and read by `merges_after` by `seq` AT READ TIME, so deleting a tombstone makes two phones disagree (the one that has folded keeps folded, the one that has not never folds); `RefMerger` on the phone has already moved the person's downloads, likes and entries onto the survivor and deleted the old row (`encore_merge.dart`), so a reverse needs a new feed and a new phone algorithm that nothing else needs. **(C) Never split, only prevent.** Rejected: the holder rule (section 1d) means the owner's collapsed library stays collapsed for ever (the album that says "1 song"), which is the symptom the owner would see every day. **A merge by file that happened while a key was empty is never undone** (a `ref_merge` row stays): a file two refs held is real evidence of one song for THAT file; what it cost is that the loser's likes and entries moved with the identity, and that is in the list below.

**9. (2) Plays and Year in Music: a play of "A" may have been the audio of B's file (the newest file is the preferred one); not separable. (3) A merge by file made while the key was empty (section 8).
