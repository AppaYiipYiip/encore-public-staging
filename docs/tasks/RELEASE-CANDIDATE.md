# Release candidate 1: what must be true before the owner is told "ready" (kept current; update it, do not rewrite it)

Written 2026-10-30 after the owner's feedback: *"your test standards are very low and what you consider a pass is not really it. Each time you claim something is tested and ready and done and when I get to use it, it is not working or has weird bugs... the quality of the product matters way more than claiming that things have been done."* The advisor went through the session transcript and agreed. This file is the plan that follows from it. Every status below is **honest**: "built, not walked" means exactly that.

## 0. The cut-line and the triage rule (D-29, advisor, 2026-10-30)

**RC1 is the core loop, working with no dead ends, silent failures or misleading controls:** install by the guide, sign in, search and browse, a tap plays the full song, like, playlists (create, rename, delete, add songs), download a song, album or playlist, play offline, sign out; plus, on an Encore server and without deleting code, hiding the request-portal leftovers (M3, M5), routing the three import screens to one (M1) and the two invitation flows to one (M2), and showing only the Encore-relevant rows on Your server (M6). **Every new owner report is triaged into `history/README.md#audit` with a line, "RC1" or "later".** Only these enter RC1: a silent failure, data loss, a control that misleads or affects other apps, a dead end in the core loop, a duplicate or dead control. **New screens, restyles and new features go to RC2, drawn first** (the frame revision pass, F46; the album wall, F47; the installer wizard, F48; a playlist's description and picture, multi-select, friends, profile editing).

**Process rule (it blocks):** a test run's exit code stops the push. `flutter test ... > log; status=$?` and push **only if `status` is 0** (the pre-commit gate runs only the packages' tests, so it cannot catch an app failure). Once a commit with six failing UI tests was pushed because a command chained the push after the run without reading it.

## 1. The definition of "pass" (from now on)

* A row **passes** only if it was **walked** on the **release-candidate pair**: the **published `:main` server image** installed **by the guide on a clean machine**, and an **APK built from the same commit**, installed fresh. Each walk is **watched to its end state** (not a snapshot), **recorded** (`adb shell screenrecord`) and written as **expected / got / verdict**.
* Anything else is labelled **"built, not walked"**. Never "done", "tested" or "fixed" for it. **Unit tests alone are never a walk.** A walk on the dev machine with hand-copied files is **not** a walk of the product (it said the opposite once: `b09`).
* **Merge rules:** merge only when **every check has finished**, polled **by run id** (a poll that timed out is not a result); after a merge, confirm **`main`'s own run** is green before the next step; **freeze `main`** from the moment the owner is told a build is ready.
* **Advisor checkpoints:** before each PR's design, before each merge, before scoring a walk, and **before telling the owner anything is ready**.
* Nothing goes to the owner until **`b11`** (the rehearsal's record) exists and the advisor has read it.

## 5a. The QA rounds before the owner gets a build (advisor, 2026-10-31, the owner's request)

The owner: give the testing agent the app to use, as a person from start to finish, **often**, "even after fixing these 41 findings: we might find new ones"; three rounds before it comes to him; then the setup on a new VM. And: buttons are sometimes hidden or not clickable under the system's three navigation buttons (back, home, recents); it happened before.

* **Each round:** wipe the app's data and install the APK fresh; walk as a new person from start to finish (connect or join, sign in, search, play, like, playlists: create, rename, delete, add; download a song, an album and a playlist; go offline; sign out); then the friend journey on the second emulator; then re-check every fixed finding, expected versus got. About 100 steps, the same report format, triaged by D-29 and D-41.
* **Both navigation modes in every round** (`adb shell cmd overlay enable com.android.internal.systemui.navbar.threebutton`, and `...navbar.gestural` to switch back; check it works on the image first): the agent compares every clickable bound in the UI dump with the navigation bar's bounds, and any overlap is a finding. Also: the keyboard covering a field, snackbars under the bar, rotation, 200 % text.
* **A regression test as well as a QA step:** the widget tests get a device profile with Android's three-button bar (a bottom inset of about 48 dp and a status bar) and run the main screens and the sheets and dialogs with it; no tappable rectangle may overlap the inset, and the mini-player and the tabs must sit above it. The app's `targetSdk` is checked: at 35 Android 15 forces edge-to-edge and a screen without safe-area padding draws under the bar.
* **Signing in:** a start-to-finish walk has to sign in, so the testing agent may sign in with the test login only, through `ui.py typefile` with TAB between the fields, and must never take a dump or screenshot while a password field is on screen. Every other rule stays (at most 10 catalogue taps, no homelab, nobody else's account).
* **Round 1** on a local integration build of the server branches (S0, S1, W-05, S2 merged into one unpushed branch, built with `docker build` on the dev VM 106: no Actions minutes) and a release APK from `task/RC1-app-batch` built with `BUILD_NUMBER` and `GIT_SHA`. **Round 2** after round 1's fixes. **Round 3** on the release-candidate pair: it doubles as the rehearsal.
* **The install test on a new VM**, after the reset (it needs the published release-candidate image): a testing agent follows the guide word for word on a fresh Ubuntu 26.04 with 4 GiB, with a snapshot taken before; the owner is told the VM id in one line. This is the clean machine the definition of pass asks for, and it means the rehearsal does not need the owner's VM 107.
* **The critic, once, after round 3 and the install test, before the owner gets a build** (the owner's request): an ordinary person who comes from Spotify and has never run a server. They install the server from the guide on the fresh VM, use the app as the owner, then join as a friend. Their output is **raw wishes and confusions** ("I wish I could...", "I do not know how to...", "why is this here?", "if only this were here"), each with the screen and the step where it happened, and what they liked. **Nobody filters it, neither the advisor nor I: only exact duplicates are removed, and the owner filters the list himself** (the one list that is his).
* The owner is given a build only after the three rounds, the install test and the critic.
